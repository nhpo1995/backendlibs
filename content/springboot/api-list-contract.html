Chốt hợp đồng từ giao diện

Giả sử màn hình cần tìm account theo tên, lọc role và phòng ban, sắp xếp theo ngày tạo mới nhất, mặc định 10 dòng. Hãy thống nhất trước tập cột trả về, chữ hoa/thường, giới hạn kích thước trang và quy ước số trang. Màn hình có thể ghi “Trang 1” dù API nhận page=0. Ví dụ thiết kế dưới đây chọn API từ 0, demo thực hành ở cuối chọn từ 1.

GET /api/accounts?q=an&role=USER&departmentId=3&page=0&size=2
GET /api/accounts/42
POST /api/accounts
PUT /api/accounts/42
DELETE /api/accounts/42

42 là định danh tài nguyên, lấy bằng @PathVariable. q, role, page là biến thể truy vấn, lấy bằng @RequestParam hoặc gom vào một đối tượng filter. JSON tạo/sửa đi qua @RequestBody. Với POST, server sinh ID, trả 201 và Location trỏ tới resource mới. PUT cập nhật tài nguyên đã có theo hợp đồng tại đây. DELETE thành công có thể trả 204 với body rỗng.

Khi giao diện có vài thao tác lặp lại, Bootstrap có thể giúp dựng form, bảng và nút. Dữ liệu vẫn đi theo luồng JS gửi request → server trả status/JSON → JS cập nhật màn hình. Dùng tab Network để đọc URL, method, header và body của đúng request. Form tạo account chỉ cập nhật danh sách sau khi server xác nhận; với lỗi validation dùng dữ liệu trả về để hiển thị lỗi đúng trường.

Tính kết quả truy vấn trước khi viết code

Dữ liệu giả định, cột ngày tạo rút gọn xuống ngày để nhìn thấy nhiều bản ghi đồng hạng.

id | username | role  | department_id | created_at
10 | An       | USER  | 3             | 2025-02-20
11 | Anh      | USER  | 3             | 2025-02-20
12 | Lan      | USER  | 3             | 2025-02-19
13 | AnAdmin  | ADMIN | 3             | 2025-02-21
14 | AnOps    | USER  | 4             | 2025-02-21

q=an là tìm chuỗi con không phân biệt hoa/thường nên cả năm tên đều khớp. Thêm role USER và department 3 còn 10, 11, 12. Sắp xếp theo ngày giảm dần, dùng ID giảm dần khi trùng ngày, rồi lấy hai dòng mỗi trang. Trang 0 là [11,10], trang 1 là [12], tổng 3 dòng và 2 trang. totalElements đếm tập sau lọc; items.length chỉ đếm trang hiện tại. Dùng cùng predicate ở truy vấn đếm. Nếu join collection nhân bản account, xét count(distinct a.id) hoặc lọc bằng exists.

interface AccountRepository extends JpaRepository<Account, Long> {
    Page<Account> findByUsernameContainingIgnoreCaseAndRoleAndDepartment_Id(
        String text, Role role, Long departmentId, Pageable pageable);
}

// Bên service. Quy ước đầu vào page từ 0.
Pageable paging = PageRequest.of(page, size,
    Sort.by(Sort.Order.desc("createdAt"), Sort.Order.desc("id")));
Page<AccountView> result = repository
    .findByUsernameContainingIgnoreCaseAndRoleAndDepartment_Id(q, role, departmentId, paging)
    .map(a -> new AccountView(a.getId(), a.getUsername()));

Đoạn thiết kế trên giả định entity Account có username, role, department, createdAt và id. Department_Id chỉ rõ đường dẫn department.id. Dùng JPQL khi cần chỉ định phép join hay constructor DTO. Dùng Specification để chỉ thêm điều kiện khi input hiện diện, vì truyền null vào derived query có thể tạo điều kiện IS NULL với phép bằng. Filter role và phòng ban phải nối AND với nhóm điều kiện tìm theo tên; nếu tìm theo username hoặc email, viết (username khớp OR email khớp) AND role khớp.

Whitelist trường sort và giới hạn size ở API. Truyền giá trị bằng bind parameter. Với JPQL LIKE tự viết, escape % và _ nếu yêu cầu tìm theo ký tự thật. Thứ tự có ID giúp phân trang xác định trên cùng dữ liệu; nếu có thêm/xóa giữa hai request, offset vẫn có thể trượt. Với danh sách ghi thường xuyên có thể nghiên cứu cursor dựa trên cặp ngày tạo và ID.

Thực hành với Page JSON và tài khoản

Mở terminal trong thư mục demo Lab Security: quyền truy cập, CSRF và log. Cần JDK 17+, Maven và PowerShell 7. Khởi động bằng hai lệnh sau.

mvn -B -ntp package
java -jar target/springboot-lessons-demo-0.1.0.jar

Ở terminal khác, chạy ba request sau. Demo chia ví dụ thành tìm account theo q và phân trang trên product. Product có sáu dòng ID 1–6. API page của demo bắt đầu từ 1. Kỳ vọng account linh, trang 2 có ID [3,4], totalElements=6, totalPages=3, ca cuối trả 401 và WWW-Authenticate: Basic.

$base = 'http://127.0.0.1:8117'
curl.exe -sS -u reader:demo-pass "$base/api/accounts?q=lin"
curl.exe -sS -u reader:demo-pass "$base/api/products/page?page=2&size=2"
curl.exe -si "$base/api/accounts?q=lin"

Gỡ lỗi: gửi lại request 401 với -u reader:demo-pass và kiểm tra status 200, giữ nguyên URL. Nếu chỉ trình duyệt gặp lỗi, so request thành công với request trong Network, kiểm tra header Basic và origin scheme + host + port. Với UI cùng origin của demo, mở ui.html trên localhost. Đổi page sang 0 để thấy 400 của demo. Nếu UI bắt đầu từ 0, chuyển đổi đúng một lần ở biên API. Kiểm tra trang cuối và trang vượt phạm vi để phát hiện sai lệch một đơn vị.

Q1. Tự triển khai API danh sách nhóm theo hợp đồng

Trong bản sao demo cổng 8117, giữ các endpoint hiện có và thêm GET /api/groups/page. Sử dụng bảng lab_groups có sẵn. Seed gồm Backend (1), Ops (2), Empty (3), cùng thời điểm 2025-02-07T08:00:00Z và creator admin. Tạo thêm một group thử ID 4, Lab, creator reader, ngày tạo mới hơn để kiểm tra lọc. Hợp đồng dùng filter creator tùy chọn, page bắt đầu từ 1, size mặc định 10 và được phép từ 1 đến 100. Whitelist order=recent|id. Mặc định recent chọn created_at DESC, id DESC. Projection mỗi item chỉ có id,name,createdAt, ngoài mảng items có page,size,totalElements,totalPages.

Điểm xuất phát. Dùng cấu trúc controller/service của demo và tự viết truy vấn dữ liệu cùng count. Có thể dùng JPQL constructor projection với entity ánh xạ lab_groups hoặc SQL với NamedParameterJdbcTemplate. Nếu lọc, cả hai truy vấn dùng cùng điều kiện creator = :creator; nếu vắng filter, bỏ điều kiện. Dùng biểu thức ORDER BY xác định trong mã cho từng khóa sort.

Query stringKỳ vọng HTTP và IDTổng và số trang
creator=admin&page=1&size=2200, [3,2]3 và 2
creator=admin&page=2&size=2200, [1]3 và 2
page=1&size=2&order=id200, [1,2]4 và 2
creator=missing200, []0 và 0
page=0 hoặc order=name400Không vào truy vấn danh sách

Gọi bằng credential mẫu như các request phía trên. Test cả khóa JSON của item, tổng trang và thứ tự ID đồng hạng. Quan sát SQL lấy items chỉ chọn các cột DTO cần. Gây lỗi bằng cách đếm toàn bảng trong ca lọc admin. Khi test thấy tổng 4 thay vì 3, sửa count để dùng cùng bộ lọc rồi chạy lại cả ca vắng lọc. Dùng ca này để giải thích vì sao chỉ kiểm danh sách ID có thể bỏ sót lỗi metadata.

Tự kiểm tra

Vì sao dùng hai trường sort?

Hai dòng có thể trùng ngày tạo. ID tạo thứ tự phân định để cùng tập dữ liệu luôn cho cùng ranh giới trang.

GET chi tiết và GET tìm kiếm khác ở đâu?

ID trên path xác định một tài nguyên. Query điều chỉnh tập và cách trình bày kết quả. Tìm không khớp trả danh sách rỗng; ID không tồn tại trả 404 theo hợp đồng này.

Chọn derived query, JPQL hay Specification?

Tên method phù hợp predicate ngắn, cố định. JPQL khi muốn điều khiển phép join hoặc dạng kết quả. Specification phù hợp tập điều kiện tùy chọn cần ghép động.

Tại sao lọc xong còn cần tổng số dòng?

UI tính số trang từ tổng sau lọc. Dùng độ dài một trang làm tổng sẽ cho sai điều hướng và số kết quả.

Ẩn nút xóa cho reader đã bảo vệ dữ liệu chưa?

UI chỉ điều chỉnh khả năng thao tác. Server vẫn phải kiểm tra quyền trên DELETE vì client có thể gửi request trực tiếp.

Vì sao có HTTP 401 dù SQL đúng?

Security filter có thể chặn request trước MVC và repository. Kiểm tra credential và header phản hồi trước khi sửa SQL.
