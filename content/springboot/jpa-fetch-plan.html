Theo dõi EAGER, LAZY và fetch join

Mặc định JPA dùng EAGER cho @OneToOne. EAGER yêu cầu quan hệ được nạp sẵn, còn LAZY là gợi ý cho provider. Hibernate có thể dùng JOIN hoặc thêm SELECT để đáp ứng yêu cầu fetch tùy truy vấn và mapping. Phía ngược của quan hệ một–một có thể cần truy vấn để xác định có detail hay không. Demo dùng LAZY ở phía có FK, nơi Hibernate có sẵn ID của detail để tạo proxy.

Với ID 1, đọc offering mà không truy cập detail chỉ cần SELECT đầu. Gọi getSpecification() trong transaction làm proxy nạp dữ liệu bằng SELECT thứ hai. Hibernate.isInitialized quan sát trạng thái trước và sau lúc gọi getter. Sau khi persistence context đóng, đọc proxy chưa nạp có thể gây LazyInitializationException. Demo chuyển sang DTO bên trong transaction và tắt Open EntityManager in View.

LEFT JOIN FETCH giữ offering số 2 dù detail_id là NULL và bảo Hibernate nạp quan hệ từ kết quả. JOIN thường dùng để điều kiện hóa dữ liệu. FETCH JOIN còn yêu cầu nạp association. Xem repository · Xem thí nghiệm Hibernate.isInitialized.

Đo số truy vấn và số dòng đọc

Chi phí có hai phần. Mỗi SELECT là một lượt ứng dụng giao tiếp với DB. Số hàng, số cột và chi phí join quyết định phần công việc của từng lượt. Đo cả hai khi chọn fetch plan.

Đọc kế hoạch SQL. Trong PostgreSQL dùng cho học tập, lấy câu SELECT phân trang ở log, thay placeholder bằng giá trị đúng kiểu từ ca nhỏ, rồi chạy EXPLAIN (ANALYZE, BUFFERS). Đọc kiểu scan, node Sort hoặc Join, số hàng kế hoạch dự đoán và số hàng thực tế qua từng node. Lệnh thực sự chạy SELECT. Với bảng products từ bài phân trang, có thể thử SELECT id, name FROM products WHERE status = 'ACTIVE' ORDER BY price, id LIMIT 20 và index ứng viên (status, price, id). Trên bảng nhỏ optimizer có thể vẫn chọn quét tuần tự. Nạp tập dữ liệu giả lớn hơn và so lượng dữ liệu đã đọc, số hàng và thời gian trước/sau khi thêm index. Thực hiện trên PostgreSQL để kết luận về kế hoạch PostgreSQL.
