Controller lấy dữ liệu từ phần nào của request?

Client gửi PUT /api/groups/1?name=Platform và gặp 400. Đường dẫn có ID đúng, nhưng handler dùng @RequestBody để nhận JSON có name. Bài luồng MVC cho biết lỗi khả năng chuyển đổi xảy ra trước method. Ở đây hãy đọc chữ ký để tìm đúng nguồn của từng đối số.

Dữ liệuNguồn Spring MVC đọcVí dụ và kết quả
Nhóm đích@PathVariable long id/api/groups/1 → 1. Dùng abc → 400 trước handler.
Bộ lọc tìm nhóm@RequestParam(name = "q", required = false) String q?q=Platform%20Core → chuỗi Platform Core. Vắng q → null theo chữ ký này.
Dữ liệu cập nhật@RequestBody GroupRequest input{"name":"Platform"} với Content-Type: application/json → DTO. Dồn vào query và bỏ body → 400.

Đối chiếu ngay trên bài. Giữ URL và JSON hợp lệ, đổi duy nhất Content-Type sang text/plain. Với handler yêu cầu JSON và cấu hình converter mặc định, dự kiến 415. Khôi phục Content-Type, đổi name thành {"value":"Platform"}, dự kiến 400 ở bước đọc JSON. Khôi phục name thành chuỗi trắng và thêm @Valid, dự kiến 400 ở bước validation.

Path, query, body và cách lần theo request

@PathVariable lấy một phần đường dẫn đã khớp route; @RequestParam lấy giá trị tên cụ thể từ tham số request; @ModelAttribute có thể gom các tham số thành DTO; @RequestBody dùng HTTP message converter để đọc payload dựa vào Content-Type. HTTP method không tự ép kiểu input: POST có thể có query và body cùng lúc. Demo thiết kế GET tìm kiếm bằng query để URL dễ lưu và chia sẻ; PUT dùng JSON vì có cấu trúc dữ liệu.

Khi đọc code lạ, tìm @RequestMapping cấp class rồi nối với mapping cấp method. Đọc chữ ký để viết request nhỏ nhất; theo lời gọi tới service và repo; đối chiếu DTO trả ra với UI. Ví dụ GET /api/groups?q=5 không có group nào vì q dò tên. Nếu gửi URL đúng nhưng HTTP method sai, kiểm tra 405 và header Allow trước khi nghi lỗi DB.

Binding và quy tắc lọc

@ModelAttribute ProductFilter filter giúp MVC bind query string vào record theo tên component. minPrice=abc sai kiểu trước khi chạy query; minPrice=350&maxPrice=200 có đúng kiểu nhưng sai quy tắc, trả 400 do kiểm tra logic. Màu và trạng thái nhận enum, demo dùng chính xác BLACK / WHITE và ACTIVE / INACTIVE. Vì nameContains escape wildcard, name=%25 tìm ký tự phần trăm thật.

Phần kết hợp truy vấn nằm ở bài Specification. So với nhiều đoạn if thêm trực tiếp vào Criteria (Xóa liên kết và tìm kiếm động), Specification gom điều kiện tái sử dụng cùng một interface; SQL cuối vẫn do JPA dựng. Nếu thêm tham số màu mà không thấy kết quả thay đổi, xác minh URL bind đúng tên, kiểm tra logic có gán spec = spec.and(...), rồi đọc SQL. Nếu truy vấn chỉ có một điều kiện cố định, derived query hoặc @Query có thể dễ đọc hơn.
