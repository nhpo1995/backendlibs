Mục tiêu và điều kiện học

Tự viết advice ánh xạ lỗi thiếu group, giữ status đúng và không lộ stack trace.

Cần biết trước: Validation, exception và HTTP status. Các bài ứng dụng có thể cần đọc trước phần dữ liệu tương ứng; dùng lộ trình để chọn kiến thức còn thiếu.

Baseline: Java 17 · Spring Boot 3.5.10 · Framework 6.2 · Security 6.5. Mỗi demo có hướng dẫn riêng; ví dụ H2 không chứng minh hành vi trên DB khác.

Từ lỗi Java đến hợp đồng HTTP

Form đăng ký cần biết hiển thị thông báo chung hay tô trường username. Cùng một 400, ca username là object dừng trước khi có DTO, còn chuỗi trắng tạo được DTO rồi vi phạm constraint. Trong hợp đồng W1, giữ status 400 và dùng INVALID_JSON cho lỗi cú pháp hoặc hình dạng body, VALIDATION_FAILED với errors[].field=username cho lỗi ràng buộc. Ca hợp lệ vẫn tiếp tục tới handler và trả 200. Mã trong bảng bên dưới là của demo chung; Spring Foundations có hợp đồng riêng với GROUP_EXISTS.

DispatcherServlet giao việc chuyển lỗi khi xử lý request MVC cho các exception resolver. @ExceptionHandler trong controller có thể xử lý lỗi cục bộ; @RestControllerAdvice áp dụng chung và serialize giá trị trả về. Với các handler có kiểu exception khác nhau, MVC xét kiểu khớp (root/cause và độ cụ thể, cùng thứ tự advice nếu nhiều advice). Không nên bắt Throwable hoặc ép tất cả thành lỗi 200; giữ trạng thái đúng để client và giám sát hiểu kết quả.

Lỗi do filter bảo mật có thể xảy ra trước MVC, nên advice này không xử lý 401/403 do Spring Security. Sử dụng entry point hoặc access denied handler nếu cần chuẩn hóa phần đó. Với ràng buộc đặt trực tiếp lên tham số MVC, tùy cơ chế có thể gặp HandlerMethodValidationException; MethodArgumentNotValidException ở đây là lỗi trên DTO được đánh @Valid.

Định dạng lỗi cho người và cho máy

ProblemDetail hỗ trợ các member chuẩn theo RFC 9457. code và errors là phần mở rộng do ứng dụng định nghĩa. Client nên dựa vào HTTP status và code để điều khiển, dùng field để tô đúng ô và dùng detail/message để hiển thị. Ví dụ thật còn có lỗi Size nếu tên đã được trim thành chuỗi rỗng. Với 500, trả lời chung cùng requestId để tra log; loại exception và cấu trúc kỹ thuật nằm ở server. Không lộ stack trace, secret hoặc echo toàn bộ body.

Với cùng một request validation, đổi Accept-Language ở demo rồi đọc JSON. Máy có thể dựa vào code và field, trong khi thông báo có thể dịch. Dùng status HTTP làm nguồn để phân loại response và giữ trường status trong ProblemDetail đồng nhất. Với 500, client chỉ cần thông báo chung và mã đối chiếu, server ghi chi tiết lỗi cùng mã đó.

Lớp cha đã đăng ký handler bao phủ lỗi MVC. Nếu thêm @ExceptionHandler(MethodArgumentNotValidException.class) cho cùng loại và media type trong chính subclass, Spring có thể báo ambiguous khi khởi tạo resolver. Cách đúng trong demo là override method protected mà lớp cha đã gọi; không thêm annotation lên một method mới cho cùng kiểu. Khi log chỉ ra lỗi xác định handler, sửa mapping trước khi nghi controller logic.

Spring Data REST và controller có hợp đồng riêng

Spring Data JPA tạo implementation của repository; nó không tự tạo HTTP API. Spring Data REST có thể xuất repository đủ điều kiện thành tài nguyên HTTP, với path, HTTP method và representation do cơ chế exporter quyết định. Có thể đặt spring.data.rest.base-path=/generated để tách namespace, cấu hình repository nào được export và vô hiệu các method ghi không cần thiết. Hình dạng HAL, quyền ghi và exposure phải được kiểm tra trước khi dùng.

Ví dụ mở rộng trong project riêng do bạn quản lý: thêm starter spring-boot-starter-data-rest, tạo entity Book có ID và title, khai báo interface BookRepository extends JpaRepository<Book, Long> {}, cấu hình base path rồi GET /generated/books. Đọc _links để tìm item; so sánh với DTO tùy chỉnh. Demo chính dùng controller vì cần tính memberCount, kiểm tra membership, quy định lỗi và phân quyền rõ ràng. Không bật exporter cho repository của demo.

Để có ví dụ đủ nhỏ để dự đoán, trong project Boot 3.5 riêng dùng Web, JPA, Data REST và H2; đặt hai file sau cùng package gốc. Bật spring.jpa.hibernate.ddl-auto=create-drop với H2 dành cho bài lab và thêm property spring.data.rest.base-path=/generated. Tạo một dòng bằng runner repo.save(new Book("Spring lab")) hoặc SQL seed. GET /generated/books với Accept: application/hal+json sẽ có _embedded.books chứa title và _links.self.href; đây là representation khác với mảng từ controller /api/groups.

Thực hành và gỡ lỗi

Tự viết. Tiếp W1 hoặc làm trong bản sao Spring Foundations. Override hai handler của ResponseEntityExceptionHandler cho JSON không đọc được và lỗi DTO. Dựng ProblemDetail theo status và mã của bảng, map danh sách field từ BindingResult. Dùng test assert application/problem+json, status khớp body và code chính xác. Với sai hình dạng JSON, kiểm không có lỗi field giả. Với vi phạm constraint, kiểm field đúng, không serialize rejected value. Thêm đối chứng ở cùng endpoint để request hợp lệ vẫn tới service. Khi chạy với Security thật, dùng admin + CSRF hợp lệ trước rồi bỏ token để tự xác định ca 403 thuộc biên nào.

Đối chiếu bằng demo chung.

Trong thư mục demo chung, chạy bằng JDK 17 trở lên và Maven. Các lệnh HTTP dùng PowerShell 7. H2 được nạp dữ liệu mẫu mỗi khi khởi động lại. Nếu thực hành theo thứ tự, hãy khởi động lại trước khi cần dùng dữ liệu gốc.

Kỳ vọng lần lượt 400 VALIDATION_FAILED, 400 INVALID_JSON, 404 NOT_FOUND và 500 INTERNAL_ERROR. Dùng requestId ở 500 để tìm đúng log Unexpected failure id=.... Response không chứa chuỗi nội bộ synthetic details. Ngoài ra thử POST với text/plain, thấy 415; nếu bỏ token ở các lệnh ghi, filter trả 403 trước khi kiểm tra JSON.

Để chủ động gây lỗi trùng handler: trong bản sao của ApiErrors, thêm method @ExceptionHandler(MethodArgumentNotValidException.class) ResponseEntity<Object> duplicate(MethodArgumentNotValidException ex) { return ResponseEntity.badRequest().build(); }. Dự đoán Maven có thể đóng gói thành công nhưng app không khởi động vì hai mapping trùng. Xóa method mới, giữ override, build lại và gọi cùng request tên trống để nhận 400 có lỗi theo trường.

Mã để đối chiếu: ApiErrors.java · Registration.java · Security.java · dữ liệu mẫu · kiểm tra HTTP.

Tự kiểm tra

Bắt tất cả Exception và trả 200 có tác hại gì?

Client, retry và hệ thống giám sát không phân biệt được thành công với thất bại.

Lỗi JSON và lỗi DTO khác nhau ở đâu?

JSON sai thì converter chưa tạo được DTO; bean validation xảy ra sau khi bind thành công.

Tại sao 500 không trả ex.getMessage()?

Thông điệp có thể chứa schema, dữ liệu hoặc chi tiết nội bộ. Trả thông báo chung và lưu thông tin có kiểm soát vào log.

Tại sao override hợp lệ mà khai báo thêm handler có thể lỗi?

Override thay một bước thực thi của lớp cha; đăng ký annotation mới tạo hai mapping cho cùng lỗi trong resolver.

Filter Security có phải lúc nào cũng gọi advice không?

Không. Từ chối trước DispatcherServlet do hệ thống xử lý lỗi của Security.

Có JpaRepository thì tự có API HTTP không?

Không. Cần controller hoặc sử dụng và cấu hình Spring Data REST riêng.

Tiêu chí kiểm chứng: 404 với ProblemDetail; lỗi bất ngờ trả 500 có mã đối chiếu, không có SQL/stack trace/password trong body.

Mở đáp án và tiêu chí

Lỗi đọc body dùng mã INVALID_JSON trong demo, lỗi constraint dùng VALIDATION_FAILED và field phù hợp. Dùng ProblemDetail với mã ổn định và test không trả raw payload.

Lỗi đi qua biên nào

Một request bị filter chặn, request khác vào MVC rồi service ném lỗi không tìm thấy. Vì sao advice MVC không mặc định xử lý cả hai?

Mở đáp án và tiêu chí

Advice thuộc cơ chế xử lý exception MVC. Filter chạy trước hoặc ngoài luồng MVC tương ứng nên dùng handler phù hợp tại tầng filter/security. Test hai response độc lập.

Tự đánh giá. Xác định được điểm chịu trách nhiệm ánh xạ mỗi lỗi, tránh dựa vào status để đoán tầng.

Advice MVC có mặc định bắt mọi lỗi security filter không?

Xem giải thích khi không dùng JavaScript
