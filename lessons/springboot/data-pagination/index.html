Mục tiêu và điều kiện học

Viết danh sách có giới hạn size và sort ổn định bằng khóa phụ ID.

Cần biết trước: SELECT, ORDER BY và query parameter. Các bài ứng dụng có thể cần đọc trước phần dữ liệu tương ứng; dùng lộ trình để chọn kiến thức còn thiếu.

Baseline: Java 17 · Spring Boot 3.5.10 · Framework 6.2 · Security 6.5. Mỗi demo có hướng dẫn riêng; ví dụ H2 không chứng minh hành vi trên DB khác.

Định nghĩa trang trước khi viết truy vấn

Danh sách có sáu sản phẩm theo ID 1..6: Mouse, Keyboard, Laptop, Laptop Stand, Monitor, Cable. Người dùng yêu cầu trang 2, kích thước 2. Endpoint dùng trang bắt đầu từ 1, nên offset là (2 - 1) × 2 = 2: bỏ qua 1 và 2, lấy 3 và 4. CSDL chỉ trả tập con cần dùng; giao diện có thể hiển thị số trang hoặc nút tải tiếp. Cắt mảng ở trình duyệt sau khi tải hết chỉ phù hợp với tập rất nhỏ.

Yêu cầuitems theo IDtotalElementstotalPages
page=1, size=2[1,2]63
page=3, size=4[]62
page=2, size=4[5,6]62
Không có kết quả sau lọc[]00

Ứng dụng kiểm tra page ≥ 1, 1 ≤ size ≤ 100 và từ chối offset vượt số nguyên 32 bit mà JPA dùng cho vị trí. totalPages tính từ tổng bản ghi khớp bộ lọc, không tính từ số item được trả trên trang. Dùng total / size + (total % size == 0 ? 0 : 1) để xử lý cả chia hết lẫn trang cuối chưa đủ. Demo chọn trả 200 và danh sách rỗng khi số trang hợp lệ nhưng vượt trang cuối.

Chạy các ví dụ trên máy

Tải bộ demo Maven (.zip). Giải nén và dùng thư mục spring-demo-bundle chứa lessons và practice làm thư mục gốc cho các lệnh trong bài. Khi bài yêu cầu vào thư mục demo, mở thư mục chứa pom.xml của demo đó.

Pageable và SQL native

Pageable chứa yêu cầu về cửa sổ và thứ tự; Page chứa dữ liệu và tổng số. Spring Data có thể chạy thêm câu COUNT, hoặc suy ra tổng trong một số trường hợp chẳng hạn trang đầu ít phần tử hơn size. Cách native trong demo lấy danh sách bằng LIMIT/OFFSET và gọi repo.count() riêng; nếu thêm WHERE, COUNT phải dùng cùng điều kiện. Trả DTO PageView với page bắt đầu từ 1 để hợp đồng JSON không lệ thuộc cấu trúc serialize của PageImpl. Cùng một yêu cầu có thứ tự ID cho ra cùng JSON ở hai mode.

Nếu chỉ cần biết còn trang tiếp hay không, Slice tránh tổng số bằng cách thường đọc thêm một phần tử (chẳng hạn 3 dòng cho size 2). List với Pageable chỉ trả nội dung. Với API quản trị cần số trang, Page là lựa chọn hợp lý; với luồng cuộn hoặc dữ liệu lớn, cân nhắc Slice hoặc keyset.

Thứ tự, dữ liệu thay đổi và chi phí

Hai sản phẩm ID 1 và 6 đều giá 100; nếu chỉ ORDER BY price, chúng đồng hạng và DB có thể đổi thứ tự giữa hai lần đọc. Ghép price ASC, id ASC, trang đầu size 2 luôn là [1,6] trên bộ dữ liệu cố định. Demo chỉ cho phép sort id hoặc price; SQL native chỉ hỗ trợ id. Không nối tên cột từ input vào SQL; bind parameter không thể đại diện cho identifier.

Ngay cả thứ tự ổn định cũng không ngăn dịch trang khi có bản ghi mới. Ví dụ ban đầu đọc trang đầu [1,2]; nếu phía trước chèn một mục có khóa nhỏ hơn, offset 2 có thể gặp lại ID 2. Với danh sách lớn, DB còn phải đi qua nhiều dòng để bỏ offset. Khi chỉ cần tải tiếp, có thể dùng WHERE id > :lastId ORDER BY id LIMIT :size, hoặc so cặp (price, id) nếu sắp theo giá. API cursor đổi cơ chế điều hướng và thường không có nhảy trực tiếp tới trang N.

Phân trang một tập có đồng hạng

Trên demo H2, gửi GET /api/products?maxPrice=200&order=price&size=2 với page=1 rồi page=2. Sau lọc còn giá 100 của ID 1, 6 và giá 200 của ID 2, 4. Thứ tự toàn phần là [1,6,2,4]. Hai trang phải lần lượt trả [1,6] và [2,4], mỗi trang báo tổng 4 dòng và 2 trang.

  1. Tự viết. Trong bản sao demo, bổ sung sort priceDesc vào whitelist. Ghép price DESC, id ASC. Giữ mặc định cũ và mode SQL theo ID. Lặp hai ca lọc, kỳ vọng [2,4] và [1,6]. Thử order=name để kiểm tra lỗi 400.
  2. Bật Hibernate SQL log. So điều kiện của SELECT lấy items và COUNT nếu Hibernate phát câu COUNT. Trang đầu đủ hai item là ca tốt để kiểm tra tập mà repository đếm. Thay bản COUNT có lọc bằng đếm toàn bảng trong bản thử và xác nhận test thất bại vì tổng 6 thay cho 4.
  3. Mô phỏng lệch trang bằng tay với thứ tự [1,6,2,4]. Sau khi client đọc [1,6], thêm ID 7 giá 50. Lượt offset tiếp theo có thể trả [6,2]. Một cursor gồm giá và ID cuối của trang trước (100,6) tiếp tục với predicate bên dưới, trả [2,4] trên seed mới. Khi giá của bản ghi thay đổi, thứ tự cũng có thể thay đổi giữa hai request. Cursor không tạo snapshot chung.
where price <= :maxPrice
and (price > :lastPrice or (price = :lastPrice and id > :lastId))
order by price asc, id asc

Dùng cùng bộ lọc, chiều sort và bộ khóa trong mọi trang liên quan đến một cursor. Nếu còn phải nhảy đến trang bất kỳ và biết tổng số, đo chi phí count và offset trước khi đổi hợp đồng.

Thực hành và gỡ lỗi

Trong thư mục demo chung, chạy bằng JDK 17 trở lên và Maven. Các lệnh HTTP dùng PowerShell 7. H2 được nạp dữ liệu mẫu mỗi khi khởi động lại. Nếu thực hành theo thứ tự, hãy khởi động lại trước khi cần dùng dữ liệu gốc.

Hai lệnh đầu trả page:2, size:2, totalElements:6, totalPages:3, items gồm Laptop và Laptop Stand. Lệnh thứ ba trả ID 1 và 6; lệnh cuối trả 400. Gọi thêm page=4&size=2 để kiểm chứng 200 với items:[]. Bật --logging.level.org.hibernate.SQL=DEBUG để nhìn truy vấn dữ liệu và truy vấn đếm.

Tái hiện lỗi đặt tên tham số trong bản sao: đổi @Param("skip") thành @Param("off") nhưng giữ :skip. Build rồi chạy và gọi mode SQL. Với demo này app khởi động được nhưng request mode SQL trả 500. Mở debugger trong bản sao, đặt breakpoint tại ApiErrors.unexpected và đọc chuỗi nguyên nhân từ exception để thấy tên bind bị thiếu; đối chiếu ngay cặp :skip và @Param("off"). Sửa cặp tên đồng nhất, rồi so lại cả nội dung và metadata ở trang 2. Nếu không gặp lỗi nhưng trang đầu thiếu hai dòng, kiểm tra nơi trừ 1: chỉ đổi từ trang 1 sang index 0 đúng một lần.

Mã để đối chiếu: Products.java · dữ liệu mẫu · kiểm tra HTTP.

Tự kiểm tra

Trang 3 size 5 bỏ qua bao nhiêu dòng?

10, tức (3 − 1) × 5.

Tổng 11 dòng, size 5 có mấy trang?

3, với số item lần lượt 5, 5, 1.

Vì sao cần thêm id vào sort theo price?

Để xác định thứ tự các dòng có cùng giá trên snapshot cố định.

Page và Slice khác gì?

Page có tổng số và số trang, có thể phải đếm; Slice chỉ biết có trang tiếp.

Nếu có filter, COUNT nào là đúng?

Cùng tập điều kiện với truy vấn lấy items, đồng thời tránh đếm trùng do join nếu cần.

Sửa Java mà DevTools không restart thì kiểm tra gì?

Kiểm tra IDE đã compile ra classpath và tiến trình đang chạy có hỗ trợ DevTools.

Cách sửa starter: Sửa biểu thức Sort trong dòng Pageable hiện có để thêm id làm khóa phụ. Thay dòng cũ, không khai báo thêm một biến page trùng tên.

Tiêu chí kiểm chứng: Hai hàng trùng tên không đổi chỗ tùy ý giữa các lần đọc cùng dữ liệu; size ngoài giới hạn → 400, page đầu là 0.

Đoạn dưới là bài tập ngắn; các kiểu và phương thức liên quan cần nằm trong project của bài. Editor cho sửa, lưu nháp và tải file; không biên dịch hoặc chạy Java/Spring. Chạy test thật ở local theo hướng dẫn project.

Kiểm tra cách hiểu

Trước khi mở đáp án, hãy ghi dự đoán, lý do và dấu hiệu bạn sẽ dùng để kiểm chứng.

Offset và tổng số

API dùng trang bắt đầu từ 1. Có 6 hàng theo ID, page=2 size=4. Nêu offset, ID trả về và totalPages.

Mở đáp án và tiêu chí

Offset 4, trả [5,6], totalPages 2. Khi dùng PageRequest, chuyển page thành 1. Tổng phải từ tập khớp filter chứ không từ hai item trả về.

Tự đánh giá. Nêu chỗ chuyển chỉ số một lần ở biên và kiểm trang vượt phạm vi.
