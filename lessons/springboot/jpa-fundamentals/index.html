Mục tiêu và điều kiện học

Ánh xạ entity tối thiểu; viết derived query theo thuộc tính Java, xác nhận SQL và kết quả.

Cần biết trước: Java object, SQL SELECT và repository. Các bài ứng dụng có thể cần đọc trước phần dữ liệu tương ứng; dùng lộ trình để chọn kiến thức còn thiếu.

Baseline: Java 17 · Spring Boot 3.5.10 · Framework 6.2 · Security 6.5. Mỗi demo có hướng dẫn riêng; ví dụ H2 không chứng minh hành vi trên DB khác.

Từ lấy một dòng đến lấy danh sách

Để đọc danh sách sản phẩm, controller nhận HTTP request, service thực hiện use case và repository truy vấn dữ liệu. Repository có findAll() và findById(id). Danh sách không có phần tử là một kết quả hợp lệ; không đồng nhất nó với việc không có tài nguyên theo một ID cụ thể.

Khi đổi từ đọc chi tiết sang danh sách, đổi kiểu hợp đồng ở cả ba tầng. Một sản phẩm dùng ProductOffering, nhiều sản phẩm dùng List<ProductOffering>. Nếu cần header/status tường minh, dùng ResponseEntity<List<ProductOffering>>. Demo trả danh sách từ RestController nên MVC ghi mảng JSON với status 200.

Với dữ liệu mẫu, GET /products trả bốn dòng. Khi danh sách rỗng, mảng JSON là []. Đọc chi tiết theo ID ở Theo dấu API từ HTTP đến cơ sở dữ liệu có hợp đồng khác vì URL chỉ đến một bản ghi cụ thể. Đoạn kiểm tra lại URL và tên đường dẫn khi gọi API. Đoạn phân biệt body và status trên công cụ gửi request.

Từ JDBC đến Spring Data JPA

Với JDBC, ứng dụng lấy Connection, tạo PreparedStatement, bind tham số, gọi executeQuery() và chuyển từng dòng từ ResultSet sang dữ liệu Java. Nhiều truy vấn lặp lại phần quản lý tài nguyên và ánh xạ. Đây là đoạn JDBC minh họa lại truy vấn tìm theo tên với một DataSource đã cấu hình.

ORM
Ánh xạ trạng thái đối tượng với dữ liệu quan hệ. Provider dùng metadata của entity để biết bảng, cột, định danh và cách đọc kiểu dữ liệu.
Jakarta Persistence (JPA)
Đặc tả API và hành vi như EntityManager, lifecycle của entity, mapping và JPQL.
Hibernate ORM
Provider triển khai JPA. Nó dịch truy vấn sang SQL theo dialect, gọi JDBC và dựng entity từ kết quả. Hibernate còn có API riêng như Session và SessionFactory. Phần so sánh JDBC và session bắt đầu tại .
Spring Data JPA
Tạo proxy cho repository, cung cấp các phương thức CRUD và suy ra truy vấn tùy theo chữ ký repository.
Spring Boot
Dùng starter và cấu hình để lắp datasource, JPA và repository khi các điều kiện tự cấu hình thỏa mãn.

Trong một persistence context, provider theo dõi entity đang được quản lý theo định danh. EntityManager cho ứng dụng làm việc với context này. EntityManagerFactory tạo các entity manager, còn connection thuộc tầng JDBC. File YAML của demo tắt Open EntityManager in View. Demo chỉ trả các thuộc tính cơ bản của entity nên có thể ghi JSON sau truy vấn. Khi đổi hệ quản trị, cần kiểm tra lại driver, dialect, kiểu cột, collation và các biểu thức SQL đặc thù. Xem thêm về cấu hình và starter.

Một hàng dữ liệu đi qua các trạng thái nào?

Giả sử H2 đã có sản phẩm ID 1 giá 100000. Chạy thử nghiệm trong một test không có transaction bọc ngoài. Dùng TransactionTemplate.executeWithoutResult để mở mỗi transaction, inject EntityManager bằng @PersistenceContext. Khai báo thử nghiệm trên bản sao demo để giữ seed nguyên gốc. Thêm dependency test-scope org.springframework.boot:spring-boot-starter-test, dùng @SpringBootTest và @Autowired TransactionTemplate tx trong test. Dùng các assertion tĩnh của JUnit Jupiter, chạy mvn test từ thư mục demo.

tx.executeWithoutResult(status -> {
    ProductOffering first = em.find(ProductOffering.class, 1L);
    ProductOffering again = em.find(ProductOffering.class, 1L);
    assertSame(first, again);
    assertTrue(em.contains(first));
    em.clear();
    assertFalse(em.contains(first));
    assertNotSame(first, em.find(ProductOffering.class, 1L));
});

Context giữ một instance được quản lý cho mỗi kiểu entity và ID. Hai lần find trước clear dùng chung instance và Hibernate dự kiến chỉ đọc SQL ở lần đầu khi context mới. clear() tách mọi instance khỏi context. Lần đọc cuối cần nạp lại trong cấu hình demo không có cache cấp hai. Biến first vẫn trỏ tới đối tượng Java cũ.

Tự viết biến thể ghi và xác nhận rollback

  1. Thêm phương thức nghiệp vụ changePrice(long) vào entity demo. Trong callback transaction, đọc ID 1, đổi giá thành 120000, gọi em.flush() rồi em.clear(). Đọc lại trong cùng transaction phải thấy 120000. Ghi lại SQL UPDATE phát ra dù không gọi save.
  2. Trước khi thoát callback, gọi status.setRollbackOnly(). Đọc ID 1 trong callback mới phải thấy 100000. Lặp lại ca ghi với commit và đọc bằng transaction mới để xác nhận 120000.
  3. Gây lại lỗi theo dõi trạng thái bằng cách clear() ngay sau khi đọc lần đầu, rồi mới sửa instance cũ. flush() sẽ không phát UPDATE. Nạp lại entity trong context và áp dụng thay đổi lên instance managed để khôi phục hành vi.

Flush đồng bộ thay đổi đang chờ xuống DB trong transaction đang mở. Commit chốt kết quả transaction. Nếu quan sát log SQL mà kết luận thao tác đã lưu bền, ca rollback sẽ bác bỏ dự đoán đó. Bài transaction tiếp theo dùng chính khác biệt này để phân tích lỗi ở service.

Ánh xạ bảng, cột và kiểu dữ liệu

@Entity đưa class vào mô hình persistence. @Table chỉ bảng, @Id chỉ định danh. Đặt @Id trên field giúp chọn field access trong entity này. Hibernate có thể dựng và điền đối tượng qua constructor không tham số và các field. Getter public của demo dùng khi Jackson ghi JSON.

  • BIGINT có dấu ánh xạ sang Long. Demo chọn Long cho giá nguyên và ID. Nếu nghiệp vụ cần phần lẻ, dùng DECIMAL với BigDecimal và quy định scale phù hợp. Các wrapper như Long có thể biểu diễn SQL NULL khi schema cho phép.
  • @Column(name = "product_name") dùng khi cột SQL khác tên field. length, nullable và unique mô tả mapping và có thể tham gia sinh DDL. Demo định nghĩa constraint thực tế trong schema.sql và dùng ddl-auto: validate. Muốn đổi ràng buộc của một bảng đã tồn tại, thay đổi schema bằng migration phù hợp. Spring MVC dùng cơ chế riêng để kiểm tra dữ liệu request.
  • insertable = false hoặc updatable = false yêu cầu provider bỏ cột khỏi câu INSERT hay UPDATE tương ứng do nó sinh. columnDefinition cho phép ghi đoạn DDL theo dialect.

Demo đọc các ID có sẵn từ SQL seed. Với API chỉ đọc, ID đã có trong bảng. Khi thêm API tạo bản ghi, bạn cần quyết định ứng dụng cấp ID hay CSDL sinh ID. Xem entity đầy đủ.

Trường tính toán, audit và vòng đời entity

Slide minh họa @Formula của Hibernate với họ tên ghép từ hai cột và số thuế tính từ thu nhập. Đây là biểu thức SQL đưa vào lệnh đọc để nhận một thuộc tính tính toán. Nó phụ thuộc cú pháp và cách xử lý NULL của DB. @Transient trong JPA loại field khỏi mapping. Nếu ghép họ tên trong một getter Java, Java thực hiện phép tính sau khi đọc dữ liệu.

Ở , lớp thảo luận các trường theo dõi người tạo, thời điểm tạo, người sửa và thời điểm sửa. Xóa mềm dùng một cờ như deleted để dữ liệu vẫn còn trong bảng. Nếu áp dụng cách này, API đọc cần lọc dòng đang hoạt động theo quy ước nghiệp vụ, chẳng hạn findByNameAndDeletedFalse. Demo đọc bảng mẫu chưa có các trường audit hay cờ xóa.

Khi JPA persist entity mới, callback thiết lập thời gian trên đối tượng trước INSERT. Hibernate có lựa chọn @CreationTimestamp, mặc định lấy thời gian từ JVM và gán khi insert. Với DEFAULT CURRENT_TIMESTAMP của database, DB đặt giá trị khi INSERT để cột dùng default, chẳng hạn khi câu SQL bỏ qua cột đó. Script seed hay JDBC trực tiếp chạy ngoài callback JPA. Đoạn so sánh hai cách đặt thời điểm lúc lưu.

Suy ra truy vấn từ tên phương thức

Bài toán tìm kiếm có hai biến thể: tìm theo tên, hoặc đồng thời theo tên và giá. Repository cung cấp findByName và findByNameAndPrice. Demo thêm OrderByIdAsc để đầu ra có thứ tự ổn định và dùng List vì có thể tìm thấy không, một hoặc nhiều sản phẩm.

Spring Data phân tích phần sau By dựa trên thuộc tính Java. Name ánh xạ đến name, AndPrice thêm phép so sánh bằng trên price, còn OrderByIdAsc thêm sắp xếp. Spring Data JPA dựng truy vấn JPA Criteria cho các phương thức này. Hibernate dịch sang SQL dùng placeholder rồi bind giá trị qua JDBC.

findByName dùng phép bằng. Tìm theo một phần tên cần phương thức có Containing. Khi khớp tên chữ hoa, chữ thường hoặc dấu, kết quả còn phụ thuộc collation của cột ở DB triển khai. Optional<ProductOffering> phù hợp với truy vấn có kỳ vọng tối đa một dòng. Tên có thể trùng, nên dùng danh sách cho bài này.

Trong live coding, lớp tạm truyền giá trị cố định. Cách nhận giá trị từ ngoài được hẹn ở . Demo bổ sung @RequestParam để tự chọn dữ liệu từ curl. Spring MVC nhận và đổi kiểu price trước khi gọi controller. Tham số thiếu hoặc sai kiểu cho HTTP 400.

Chẩn đoán lỗi theo dấu hiệu

  1. Ứng dụng không khởi động sau khi thêm repository method. Trong bản thử, đổi findByNameAndPriceOrderByIdAsc thành findByNamePriceOrderByIdAsc ở cả repository và lời gọi trong service. Build và chạy lại. Khi đọc Could not create query, tìm PropertyReferenceException. Spring Data thử duyệt ProductOffering.name rồi tìm thuộc tính price trên String. Khôi phục And, chạy lại và kiểm tra ID 1, 4. Nếu đổi tên bằng công cụ Rename của IDE, kiểm tra cả khai báo và nơi gọi trước khi chạy lại.
  2. Ứng dụng chạy nhưng truy vấn nhận ID null. Id must not be null nghĩa là repository nhận null, dù API có thể đã nhận một URL hợp lệ. Lần ngược tới lời gọi findById để kiểm tra ID có được truyền từ controller sang service hay bị thay bằng biến chưa được gán. Khi tự tái hiện trên Theo dấu API từ HTTP đến cơ sở dữ liệu, truyền null vào lời gọi repository.findById trong bản thử, quan sát log rồi trả lại ID từ controller. Với JDBC, ORM và Spring Data JPA, thử bỏ price khỏi URL và kiểm tra HTTP 400 ngay tại bước bind.
  3. 200 với mảng rỗng. Kiểm tra giá trị tham số, phép so sánh bằng, đúng bảng và dữ liệu mẫu. Dùng SQL tương đương hoặc thử lại bằng dữ liệu chắc chắn có. Để phân biệt lỗi truy vấn và dữ liệu không khớp, hãy đổi giá của một dòng trong data.sql rồi khởi động lại demo H2. Gọi lại URL với giá cũ và giá mới để kiểm tra dòng đó rời hoặc gia nhập tập kết quả đúng như điều kiện WHERE.

Tự kiểm tra

1. Tên Product A và giá 100000 trả bao nhiêu dòng?

Hai dòng, ID 1 và 4. ID 2 trùng tên nhưng khác giá. ID 3 trùng giá nhưng khác tên. Hai điều kiện nối bằng AND.

2. Ai phân tích findByNameAndPrice, ai sinh SQL?

Spring Data JPA phân tích tên phương thức repository và dựng truy vấn JPA. Hibernate dịch truy vấn sang SQL cho dialect hiện tại rồi dùng JDBC để chạy với các tham số đã bind.

3. Đổi tên cột SQL thành product_name thì sửa gì?

Đổi schema và đặt @Column(name = "product_name"). Giữ findByName... khi field Java vẫn tên name.

4. Vì sao giá abc cho 400 còn giá 123 cho 200 []?

MVC đổi chuỗi sang Long trước khi gọi controller. abc lỗi chuyển kiểu. 123 hợp lệ về kiểu và truy vấn chạy, nhưng bộ seed thiếu dòng khớp.

5. Vì sao đổi chữ ký thành Optional<ProductOffering> có thể làm hỏng API?

Chữ ký đó kỳ vọng nhiều nhất một bản ghi. Bộ seed cố ý có nhiều dòng trùng tên, thậm chí trùng cả tên và giá. Hãy để kiểu List<ProductOffering> biểu diễn mọi kết quả.

6. @PrePersist có chạy khi chạy INSERT trong cửa sổ SQL không?

Callback thuộc vòng đời do JPA quản lý. INSERT trực tiếp có thể dùng giá trị do DB tạo nếu cột có default và câu lệnh để cột dùng default.

7. Làm sao đổi bài tập thành tìm tên chứa một từ và màu đỏ?

Dùng findByNameContainingAndColorOrderByIdAsc(String name, String color) rồi nối tham số ở service và controller. Với Product và red, bộ seed cho ID 1. Đây là bài mở rộng để phân biệt LIKE và phép bằng.

Khi tự học xong, bạn có thể giải thích luồng từ hai tham số URL đến hai vị trí bind, dự đoán kết quả từ SQL seed, rồi tự gây và sửa lỗi thiếu And ở repository.

Kiểm tra cách hiểu

Trước khi mở đáp án, hãy ghi dự đoán, lý do và dấu hiệu bạn sẽ dùng để kiểm chứng.

SQL, entity và JSON

Đổi tên JSON của name nhưng giữ nguyên cột product_name và thuộc tính Java name. Derived query findByName và SQL native dùng tên gì?

Mở đáp án và tiêu chí

Derived query dựa trên name trong Java. SQL native dùng product_name. Tên JSON chỉ thuộc biên serialize. Kiểm cùng kết quả bằng seed và xem SQL được sinh.

Tự đánh giá. Gọi đúng ba lớp tên và không suy từ thay đổi JSON sang đổi schema.

Entity managed và detached

Trong transaction, sửa name của entity vừa load mà không gọi save. Sau đó lấy entity đã detached, đổi name ngoài transaction. Hai lần sửa khác nhau thế nào?

Mở đáp án và tiêu chí

Bản managed được dirty checking và flush khi phù hợp. Sửa bản detached chỉ đổi object Java nếu chưa đưa thay đổi vào context. Đọc lại sau hai giao dịch để phân biệt.

Tự đánh giá. Giải thích vai trò persistence context và kiểm từ lần đọc độc lập.
