Mục tiêu và điều kiện học

Tự viết projection ID/name và endpoint đối chiếu mapper; xác nhận cả JSON lẫn cột SELECT.

Cần biết trước: Entity JPA, repository và DTO; Specification học ở bài riêng. Các bài ứng dụng có thể cần đọc trước phần dữ liệu tương ứng; dùng lộ trình để chọn kiến thức còn thiếu.

Baseline: Java 17 · Spring Boot 3.5.10 · Framework 6.2 · Security 6.5. Mỗi demo có hướng dẫn riêng; ví dụ H2 không chứng minh hành vi trên DB khác.

DTO là hợp đồng, projection là cách lấy dữ liệu

Ứng dụng có entity Product với id, name, price, color, status. Danh sách chọn sản phẩm chỉ cần id và name, ví dụ {"id":1,"name":"Mouse"}. Nếu trả entity, việc thêm thuộc tính lưu trữ hay quan hệ lazy có thể thay đổi JSON hoặc kích hoạt truy vấn ngoài ý muốn. Chọn rõ DTO cho từng use case: DTO nhập chứa trường người gọi được phép gửi; DTO trả về chứa trường client cần biết.

CáchCột DB đọcKhi phù hợp
Mapper viết tay từ entityThường đủ cột entityCần gộp, đổi tên hoặc tính giá trị với quy tắc rõ ràng.
ModelMapper map sang DTOKhông thay đổi query lấy entityNhiều thuộc tính trùng tên và kiểu; khai báo mapping tường minh khi lệch.
JPQL constructor projectionChỉ cột xuất hiện trong constructor expressionĐọc danh sách ít trường hoặc tránh tải object thừa.

Summary có constructor đúng thứ tự và kiểu vì là record. Cách ModelMapper dùng JavaBean có constructor không tham số và setter tương ứng, ví dụ setName(String name). STRICT giảm khớp nhầm, nhưng không đảm bảo DTO mới có dữ liệu đúng. Nếu đổi destination từ name sang label, thêm mapper.typeMap(Product.class, NamedView.class).addMapping(Product::getName, NamedView::setLabel) (với DTO có setter tương ứng), rồi kiểm tra giá trị và kiểu. Không tự map toàn bộ request nhạy cảm sang entity; set rõ những trường được phép đổi.

Chọn dữ liệu ở điểm đọc

Với hai dòng seed đầu (1, Mouse) và (2, Keyboard) theo thứ tự ID, tên, danh sách chọn sản phẩm chỉ cần id và label. Field label bằng tên sản phẩm. Dự đoán JSON trước, rồi đối chiếu hai cách lấy dữ liệu bằng log SQL.

Cách triển khaiSQL dự kiếnKết quả hai dòng đầu
Đọc entity rồi tạo DTOĐọc các cột đã ánh xạ trong Product1 → Mouse, 2 → Keyboard
Constructor projection new NameOption(p.id,p.name)Chọn hai cột id, name1 → Mouse, 2 → Keyboard

Tự viết. Thêm record NameOption(Long id, String label), một truy vấn constructor với tên lớp đầy đủ và một test repository xác nhận hai dòng đầu. Ở lớp trả JSON, test bảo đảm field label có giá trị và tập khóa của item chỉ gồm id,label. Bật org.hibernate.SQL ở DEBUG trong bản chạy học tập và so SQL với endpoint mapped bên dưới ở context mới. Để tập chẩn đoán, đổi thứ tự hai đối số của constructor, quan sát lỗi không tìm được constructor tương thích khi Hibernate kiểm tra hoặc thực thi query, rồi sửa lại và chạy cả test repository lẫn JSON.

Projection interface đóng có accessor tương ứng thuộc tính entity và Spring Data có thể chỉ chọn các dữ liệu cần cho những accessor đó. Khi truy cập thuộc tính lồng qua join, lượng dữ liệu đọc có thể lớn hơn số field JSON. Kiểm SQL của từng truy vấn. Nếu cần tính toán nghiệp vụ dựa trên entity đã có, mapper viết tay giữ quy tắc rõ ràng.

Thực hành: JSON giống nhau, dữ liệu đọc có thể khác

Chạy demo chung ở cổng 8117. Hai endpoint sau trả sáu object chỉ có ID/name, nhưng một bên dùng projection còn bên kia map từ entity.

So SELECT trong log: projection lấy cột đã chọn; mapped endpoint đọc entity rồi thu nhỏ JSON. Tự thêm field label và mapping tường minh, xác nhận giá trị đúng. Tiếp theo thử đổi thứ tự/tham số constructor projection trong bản sao để thấy lỗi và cách xác nhận đã sửa.

Đối chiếu Products.java; phần tìm kiếm được học ở bài Criteria/Specification.

Tự kiểm tra

JSON chỉ có hai field có chứng minh DB chỉ đọc hai cột?

Không. Kiểm SQL và cách query, không suy từ JSON cuối cùng.

Mapper khớp tên có đảm bảo quy tắc nghiệp vụ?

Không. Field lệch tên/kiểu và dữ liệu nhạy cảm cần mapping được chọn rõ và test.

Kiểm tra cách hiểu

Trước khi mở đáp án, hãy ghi dự đoán, lý do và dấu hiệu bạn sẽ dùng để kiểm chứng.

Cùng JSON, khác SELECT

A tải entity rồi map id/name. B query DTO projection id/name. JSON giống nhau. Làm sao chứng minh B đọc ít dữ liệu hơn trong lab?

Mở đáp án và tiêu chí

Giữ seed và bộ lọc, bật quan sát SQL, so danh sách cột và số query. DTO hóa sau query không đổi SQL đã phát.

Tự đánh giá. Đưa ra bằng chứng ở tầng truy vấn, không kết luận từ response JSON.

Thêm cột tính tổng

Danh sách group cần thêm memberCount. Thiết kế query để tránh gọi count riêng trong mapper cho từng group, kể cả nhóm rỗng.

Mở đáp án và tiêu chí

Dùng aggregate với join phù hợp hoặc query gom nhóm theo tập ID. Với left join, đếm khóa của bản ghi liên kết để nhóm rỗng có 0. Kiểm cả kết quả và số query.

Tự đánh giá. Giữ nhóm rỗng và chứng minh không có một COUNT cho mỗi hàng.

Ôn nhanh bằng trắc nghiệm
Map entity thành DTO sau query có tự giảm cột SELECT không?

Xem giải thích khi không dùng JavaScript

Không; fetch/projection ở tầng query mới quyết định dữ liệu đọc. Biến đổi object sau khi đọc không làm DB quay lại chọn ít cột hơn.
