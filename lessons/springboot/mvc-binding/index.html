Mục tiêu và điều kiện học

Viết controller nhận ID ở path, bộ lọc ở query và DTO ở body theo thao tác.

Cần biết trước: HTTP, MVC request flow và kiểu dữ liệu Java. Các bài ứng dụng có thể cần đọc trước phần dữ liệu tương ứng; dùng lộ trình để chọn kiến thức còn thiếu.

Baseline: Java 17 · Spring Boot 3.5.10 · Framework 6.2 · Security 6.5. Mỗi demo có hướng dẫn riêng; ví dụ H2 không chứng minh hành vi trên DB khác.

Controller lấy dữ liệu từ phần nào của request?

Client gửi PUT /api/groups/1?name=Platform và gặp 400. Đường dẫn có ID đúng, nhưng handler dùng @RequestBody để nhận JSON có name. Bài luồng MVC cho biết lỗi khả năng chuyển đổi xảy ra trước method. Ở đây hãy đọc chữ ký để tìm đúng nguồn của từng đối số.

Dữ liệuNguồn Spring MVC đọcVí dụ và kết quả
Nhóm đích@PathVariable long id/api/groups/1 → 1. Dùng abc → 400 trước handler.
Bộ lọc tìm nhóm@RequestParam(name = "q", required = false) String q?q=Platform%20Core → chuỗi Platform Core. Vắng q → null theo chữ ký này.
Dữ liệu cập nhật@RequestBody GroupRequest input{"name":"Platform"} với Content-Type: application/json → DTO. Dồn vào query và bỏ body → 400.

Đối chiếu ngay trên bài. Giữ URL và JSON hợp lệ, đổi duy nhất Content-Type sang text/plain. Với handler yêu cầu JSON và cấu hình converter mặc định, dự kiến 415. Khôi phục Content-Type, đổi name thành {"value":"Platform"}, dự kiến 400 ở bước đọc JSON. Khôi phục name thành chuỗi trắng và thêm @Valid, dự kiến 400 ở bước validation.

Chạy các ví dụ trên máy

Tải bộ demo Maven (.zip). Giải nén và dùng thư mục spring-demo-bundle chứa lessons và practice làm thư mục gốc cho các lệnh trong bài. Khi bài yêu cầu vào thư mục demo, mở thư mục chứa pom.xml của demo đó.

Path, query, body và cách lần theo request

@PathVariable lấy một phần đường dẫn đã khớp route; @RequestParam lấy giá trị tên cụ thể từ tham số request; @ModelAttribute có thể gom các tham số thành DTO; @RequestBody dùng HTTP message converter để đọc payload dựa vào Content-Type. HTTP method không tự ép kiểu input: POST có thể có query và body cùng lúc. Demo thiết kế GET tìm kiếm bằng query để URL dễ lưu và chia sẻ; PUT dùng JSON vì có cấu trúc dữ liệu.

Khi đọc code lạ, tìm @RequestMapping cấp class rồi nối với mapping cấp method. Đọc chữ ký để viết request nhỏ nhất; theo lời gọi tới service và repo; đối chiếu DTO trả ra với UI. Ví dụ GET /api/groups?q=5 không có group nào vì q dò tên. Nếu gửi URL đúng nhưng HTTP method sai, kiểm tra 405 và header Allow trước khi nghi lỗi DB.

Binding và quy tắc lọc

@ModelAttribute ProductFilter filter giúp MVC bind query string vào record theo tên component. minPrice=abc sai kiểu trước khi chạy query; minPrice=350&maxPrice=200 có đúng kiểu nhưng sai quy tắc, trả 400 do kiểm tra logic. Màu và trạng thái nhận enum, demo dùng chính xác BLACK / WHITE và ACTIVE / INACTIVE. Vì nameContains escape wildcard, name=%25 tìm ký tự phần trăm thật.

Phần kết hợp truy vấn nằm ở bài Specification. So với nhiều đoạn if thêm trực tiếp vào Criteria (Xóa liên kết và tìm kiếm động), Specification gom điều kiện tái sử dụng cùng một interface; SQL cuối vẫn do JPA dựng. Nếu thêm tham số màu mà không thấy kết quả thay đổi, xác minh URL bind đúng tên, kiểm tra logic có gán spec = spec.and(...), rồi đọc SQL. Nếu truy vấn chỉ có một điều kiện cố định, derived query hoặc @Query có thể dễ đọc hơn.

Chuyển kiểu, validation và nghiệp vụ

Với Long minPrice, vắng tham số có thể biểu diễn bằng null; primitive long không biểu diễn được trạng thái thiếu theo cùng cách. Content-Type mô tả định dạng payload, còn Accept mô tả định dạng client muốn nhận. JSON hỏng, enum không tồn tại, giá trị sai kiểu và tên trắng là các lỗi khác nhau, dù nhiều trường hợp cùng được ánh xạ thành 400.

Gỡ lỗi theo thứ tự: mapping có khớp method/path không → converter có đọc được body không → tham số có chuyển kiểu được không → validation có đạt không → service có chấp nhận quy tắc dữ liệu không. Bắt mọi exception rồi đổi thành “không tìm thấy” sẽ che lỗi input hoặc lỗi server.

Thực hành: thay một phần request mỗi lần

Chạy solution Spring Foundations ở cổng 8181. ID 999999 giả định không tồn tại; credential chỉ của lab.

Dự kiến 400, 404 và 200. Đoạn editor luyện path bằng ID, còn ca query/body cần test theo chữ ký handler thực tế. Trong bản sao starter, tự triển khai GET /api/groups?q=... bằng tham số tùy chọn. Seed Backend/Ops, kiểm q vắng trả cả hai, q=back trả Backend theo chính sách tìm không phân biệt hoa thường, q=xyz trả mảng rỗng. Với PUT, viết hai request dùng cùng ID có thật: gửi name chỉ ở query, rồi gửi name trong JSON với Content-Type đúng. Dùng admin và CSRF hợp lệ như GroupApiTest. Test đạt khi ca đầu trả 400 và tên cũ giữ nguyên, ca sau trả 200 và GET phản ánh tên mới.

Bộ lọc ProductFilter đầy đủ nằm tại Products.java của demo chung.

POST có thể nhận query parameter và JSON body cùng lúc không?

Có. Method HTTP không tự giới hạn mọi nguồn tham số. Thiết kế API phải chỉ rõ mỗi giá trị ở đâu và cách xử lý xung đột.

Kiểm tra cách hiểu

Trước khi mở đáp án, hãy ghi dự đoán, lý do và dấu hiệu bạn sẽ dùng để kiểm chứng.

Ba nguồn đầu vào

Thiết kế PUT /products/5?notify=true với body có name. Dữ liệu nào bind qua path, query và body? Nếu URL dùng abc thì service có nên chạy?

Mở đáp án và tiêu chí

ID qua @PathVariable, notify qua @RequestParam và name trong DTO @RequestBody. abc không chuyển được thành kiểu ID nên method không chạy.

Tự đánh giá. Nêu annotation, kiểu và test request riêng cho lỗi path/body.

Kiểm tra kiểu hay quy tắc

GET list nhận Long minPrice và Long maxPrice. So minPrice=abc với minPrice=350&maxPrice=200, giả sử hợp đồng từ chối khoảng đảo.

Mở đáp án và tiêu chí

Ca abc lỗi conversion trước controller; cặp 350/200 bind được và cần quy tắc validation/nghiệp vụ. Cả hai có thể trả 400 nhưng khác tầng.

Tự đánh giá. Chỉ ra một dấu hiệu để xác định conversion đã thành công ở ca thứ hai.

Xem giải thích khi không dùng JavaScript

Thiết kế DTO bỏ ID, hoặc từ chối xung đột nếu contract có cả hai. Một nguồn định danh tránh ambiguity. Nếu hỗ trợ hai nguồn, contract phải chỉ rõ và kiểm tra xung đột.
