Mục tiêu và điều kiện học

Viết POST tạo sản phẩm và PUT cập nhật có kiểm tra tồn tại, không biến PUT nhầm thành insert.

Cần biết trước: GET API, DTO và JPA cơ bản. Các bài ứng dụng có thể cần đọc trước phần dữ liệu tương ứng; dùng lộ trình để chọn kiến thức còn thiếu.

Baseline: Java 17 · Spring Boot 3.5.10 · Framework 6.2 · Security 6.5. Mỗi demo có hướng dẫn riêng; ví dụ H2 không chứng minh hành vi trên DB khác.

POST, save và định danh

Admin tạo nhóm Platform và nhận thông báo thành công nhưng không biết mở URL nào để đọc lại. Chốt hợp đồng HTTP trước khi chọn cách ghi. Ôn DTO ghi và entity managed, flush, commit để theo các ví dụ JPA bên dưới. Spring Foundations dùng JDBC để kiểm cùng hành vi HTTP mà không cần học cách Hibernate phát hiện thay đổi trước.

Giả sử seed mới chỉ có Backend và Ops. ID 3 minh họa lần ghi đầu. Client dùng Location thực tế để GET và đối chiếu với response. Thiết kế POST nhận name, server cấp ID. Lần gửi POST thứ hai với cùng tên có thể bị ràng buộc trùng tên trả 409, chứ không phải đặc tính mặc định của mọi POST.

Khi client gửi tên, giá và màu cho POST, controller nhận dữ liệu, service tạo entity và yêu cầu repository lưu. Sau đó có thể gọi GET bằng ID trả về để xác nhận bản ghi đã được lưu. @RequestBody chuyển JSON sang kiểu Java. Service chuẩn bị entity, repository chuyển thao tác ghi cho EntityManager. Kết quả của save là đối tượng cần dùng để dựng HTTP response.

Mặc định, Spring Data JPA dùng @Version kiểu wrapper nếu có, rồi mới đến ID khi entity không có version phù hợp. Demo không có @Version. Entity có ID null được coi là mới và đi qua persist. ID đã gán thường đi qua merge theo quy tắc này. merge chép trạng thái vào một instance được quản lý và trả instance đó. Câu SQL cụ thể còn tùy trạng thái entity, bộ sinh ID và dữ liệu đang có.

Giả sử API tạo mới nhận thẳng entity và dùng save. Nếu client gán ID của bản ghi đang tồn tại, Spring Data JPA có thể chọn merge và cập nhật bản ghi đó. Hãy dùng DTO chỉ nhận các trường được phép ghi. Nếu ID để trống mà mapping vẫn yêu cầu gán thủ công, Hibernate sẽ báo lỗi khi persist. Cột tự tăng trong DB và cấu hình IDENTITY cần đi cùng nhau để Hibernate làm INSERT và nhận lại ID. Demo dựng entity từ DTO có các trường được phép sửa nên một giá trị id gửi thêm không thể điều khiển ID.

SEQUENCE lấy giá trị từ sequence của DB. TABLE dùng bảng cấp số. UUID tạo UUID, còn AUTO để provider chọn theo loại ID và nền tảng. Mỗi cách cần schema tương ứng. Xem entity.

Map enum và đồng bộ schema

Với kiểu Java Status, chỉ có hai giá trị ACTIVE và INACTIVE. Jackson mặc định chuyển chuỗi JSON theo tên hằng enum. Nếu gửi ARCHIVED, request demo lỗi trong bước đọc body và trả 400 trước khi gọi service.

STRING lưu tên hằng, còn ORDINAL lưu vị trí bắt đầu từ 0. Việc chèn hoặc đổi thứ tự enum làm đổi ý nghĩa dữ liệu cũ khi dùng ordinal. Khi đổi tên hằng lưu dạng chuỗi, cần migration dữ liệu. Ví dụ, ORDINAL bind giá trị số trong khi schema có thể yêu cầu giá trị chuỗi. Khi ghi lỗi hoặc đọc ra trạng thái sai, đối chiếu kiểu bind và DDL. JSON hợp lệ chỉ xác nhận bước đọc request, chưa xác nhận mapping xuống CSDL. Demo dùng cột VARCHAR(8) có CHECK để kiểm tra hai giá trị hợp lệ ở DB.

PUT theo ID và dirty checking

Với PUT /buoi-03/products/1, URI xác định sản phẩm số 1 và body cung cấp tên, giá, màu, trạng thái mới. Service tìm entity theo ID trong transaction rồi sửa bốn thuộc tính. Hibernate theo dõi thay đổi của entity còn managed và phát SQL khi flush, thường trước commit hoặc sớm hơn khi cần đồng bộ. Flush có thể báo lỗi constraint. Sau commit thành công, một GET độc lập mới xác nhận được thay đổi còn tồn tại. Nếu ID vắng, service trả 404 trước khi cập nhật.

Demo dùng khóa ghi khi đọc bản ghi để đồng bộ với API gán ở DTO, validation và thay thế tập liên kết. Với PUT ở đây, client gửi đầy đủ tên, giá, màu và trạng thái. Gửi lại cùng dữ liệu đưa resource về cùng trạng thái. POST tạo ID mới cho mỗi lần tạo hợp lệ. Giá trị ID gửi dư trong body không ảnh hưởng đến bản ghi đích.

Thực hành

Tự viết trên Spring Foundations. Hoàn thành POST/PUT trong starter. GET danh sách lấy seed. Gọi POST với tên mới, assert 201, Location và ID trong body khớp, rồi GET theo Location. Gọi PUT trên ID đó để đổi tên và lặp lại payload, kiểm cùng ID và số nhóm giữ nguyên. Thử PUT ID 999999 và xác nhận 404 cùng danh sách giữ nguyên. Chạy mvn -f practice/spring-foundations/starter/pom.xml -Dtest=GroupApiTest test. Mở rộng test cho ca lặp PUT và ID vắng. Test ghi cần admin và CSRF hợp lệ.

Tự đối chiếu ngay trên bài. Sau khi Platform có ID 3, đặt trong body PUT ID 2 và tên mới. Đích ghi phải được lấy từ URL /api/groups/3. Với chính sách nhận trường dư của demo sản phẩm, bản ghi 3 đổi còn bản ghi 2 giữ nguyên. Với chính sách nghiêm ngặt của bài hợp đồng danh bạ, xử lý dừng sớm với 400. Cả hai cần test đọc lại hai ID.

Đối chiếu bằng demo JPA.

Chuẩn bị JDK 17 trở lên và Maven. Chạy lệnh dưới đây từ thư mục giải nén chứa lessons và practice. Demo dùng H2 trong bộ nhớ và nạp lại bộ dữ liệu ban đầu mỗi lần khởi động. Dừng bằng Ctrl+C khi thực hành xong.

Maven Schema Dữ liệu mẫu Cấu hình

Chạy từng dòng dưới đây trong cửa sổ PowerShell thứ hai trên dữ liệu vừa khởi động. Invoke-RestMethod hiển thị body thành đối tượng. Dùng -StatusCodeVariable với PowerShell 7 nếu muốn in status của lệnh thành công.

Kỳ vọng POST trả 201 và ID 3 khi đây là lần tạo đầu. PUT trả 200, đúng ID vừa tạo và giá 135000. Sản phẩm 2 vẫn có giá 150000. Đổi URL thành ID 999 để quan sát 404. Với ID hợp lệ, lần lượt thử status: "ARCHIVED", status: 0 hoặc price: 135000.9. Cả ba trả 400 ở bước đọc JSON. Gọi GET bằng ID vừa tạo để xác nhận bản ghi giữ giá trị của lần cập nhật thành công.

@Enumerated điều khiển cách JPA ghi trạng thái xuống DB. Jackson xử lý định dạng của trạng thái trong JSON. Demo bật fail-on-numbers-for-enums và tắt accept-float-as-int để từ chối số dùng làm thứ tự enum và số thập phân truyền vào trường Long.

Để tái hiện lỗi thiếu bộ sinh ID, sao chép demo, bỏ @GeneratedValue trong ProductOffering, khởi động lại rồi gọi POST. Tìm lỗi ID phải được gán trước khi persist. Khôi phục annotation và chạy lại cùng request để thấy INSERT nhận ID do DB tạo.

Tự kiểm tra

1. Vì sao có cột tự tăng mà bỏ @GeneratedValue vẫn lỗi?

Provider cần biết ID do DB sinh. Với mapping ID gán thủ công, entity mới có ID null không đáp ứng hợp đồng persist.

2. PUT /3 mang id=2 trong body sửa bản ghi nào?

Bản ghi 3. Controller lấy ID từ URL, DTO chỉ chuyển các trường nghiệp vụ và service lấy đúng entity theo ID.

3. Đổi thứ tự hằng enum ảnh hưởng kiểu lưu nào?

ORDINAL phụ thuộc thứ tự khai báo. STRING vẫn đọc được nếu tên hằng giữ nguyên.

4. Vì sao sửa thuộc tính trong update mà không gọi save vẫn ghi xuống?

Entity được load trong transaction và còn managed. Hibernate phát hiện thay đổi khi flush.

5. PUT ID vắng sẽ tạo sản phẩm mới trong demo chứ?

API này xác định cập nhật bản ghi có sẵn. ID vắng dẫn đến 404 trước bước ghi.

Bài tập lập trình

Viết POST tạo sản phẩm và PUT cập nhật có kiểm tra tồn tại, không biến PUT nhầm thành insert.

Cách sửa starter: Giữ endpoint POST; thay TODO bằng gọi service và trả 201/Location. Editor đối chiếu riêng POST; phần PUT và lỗi ID thiếu được kiểm chứng thêm trong project.

Tiêu chí kiểm chứng: POST trả 201 + Location đọc lại được. PUT ID không có trả 404 theo contract bài này, dữ liệu cũ không bị thay nhầm.

Đoạn dưới là bài tập ngắn; các kiểu và phương thức liên quan cần nằm trong project của bài. Editor cho sửa, lưu nháp và tải file; không biên dịch hoặc chạy Java/Spring. Chạy test thật ở local theo hướng dẫn project.

Nháp tự lưu khi trình duyệt cho phép. Không nhập mật khẩu hoặc token thật.

Kiểm tra cách hiểu

Trước khi mở đáp án, hãy ghi dự đoán, lý do và dấu hiệu bạn sẽ dùng để kiểm chứng.

POST với ID do client gửi

Nhận thẳng entity rồi save, client gửi ID đang tồn tại. Rủi ro gì? Thiết kế cách chứng minh POST luôn tạo theo hợp đồng.

Mở đáp án và tiêu chí

Tùy quy tắc nhận diện entity mới, save có thể đi qua merge và ghi đè. Dùng DTO không nhận ID, tạo entity mới; kiểm 201, Location và GET lại cả bản ghi cũ/mới.

Tự đánh giá. Nêu điều kiện dẫn đến cập nhật nhầm và kiểm dữ liệu chứ không chỉ status.

PUT vào tài nguyên không tồn tại

Hợp đồng PUT sửa sản phẩm hiện có. ID 999 không có. Nếu service tạo entity mới khi lookup rỗng, test nào bắt được?

Mở đáp án và tiêu chí

Ca phải trả 404 và không insert. Dùng seed cố định, gọi PUT rồi đọc DB hoặc danh sách từ lần đọc riêng, đối chiếu tổng số và ID.

Tự đánh giá. Kiểm 404 và chứng minh bảng không có hàng mới.
