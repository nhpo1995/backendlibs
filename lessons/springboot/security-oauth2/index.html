Mục tiêu và điều kiện học

Lập checklist xác minh access token; không coi decode JWT là xác thực.

Cần biết trước: Authentication, authorization, HTTPS và JSON. Các bài ứng dụng có thể cần đọc trước phần dữ liệu tương ứng; dùng lộ trình để chọn kiến thức còn thiếu.

Baseline: Java 17 · Spring Boot 3.5.10 · Framework 6.2 · Security 6.5. Mỗi demo có hướng dẫn riêng; ví dụ H2 không chứng minh hành vi trên DB khác.

API danh bạ nhận bearer access token

Worker lời mời cần đọc nhóm qua API danh bạ bằng access token của test issuer. Theo dõi chỗ credential đi vào khác Basic và chỗ hai cơ chế gặp nhau, rồi dùng authority để phân biệt token bị từ chối với token hợp lệ thiếu quyền.

Ba khái niệm không thể dùng thay nhau

Ứng dụng muốn cho người dùng đăng nhập bằng một nhà cung cấp danh tính và gọi API danh bạ. Có ba câu hỏi: client biết user là ai bằng cách nào, client được quyền gọi API gì, và API xác minh bằng chứng nhận được thế nào.

  • OAuth 2.0 là framework ủy quyền. Các vai trò gồm resource owner, client, authorization server và resource server.
  • OpenID Connect bổ sung lớp danh tính trên OAuth 2.0, có ID token phục vụ client kiểm tra việc đăng nhập.
  • JWT là định dạng biểu diễn claims. Access token có thể là JWT hoặc opaque; một chuỗi JWT không tự tạo thành hệ thống đăng nhập an toàn.

Trong flow Authorization Code với PKCE, người dùng được chuyển tới authorization server, client nhận code qua redirect đã đăng ký rồi đổi code theo giao thức. Không gửi mật khẩu người dùng cho mọi ứng dụng client hoặc tự dựng endpoint phát JWT như cách thay thế OIDC tùy ý. Lựa chọn flow phải theo loại client và hướng dẫn bảo mật hiện hành.

Decode được không có nghĩa là đáng tin

Phần payload JWT có thể đọc được mà chưa kiểm signature. API chỉ nên tin claims sau các kiểm tra mật mã và policy phù hợp: thuật toán/key tin cậy, issuer, thời hạn và audience mục tiêu. Không nhận thuật toán do token khai báo rồi bỏ qua cấu hình tin cậy của server.

Với Resource Server JWT của Spring Security, cấu hình issuer giúp thiết lập decoder và việc xác minh liên quan. Kiểm tra audience phải được cấu hình rõ, không mặc định suy ra mọi token của issuer đều dành cho API này. Scope/authority là bước quyết định quyền sau xác thực; token hợp lệ vẫn có thể thiếu quyền.

Cần dependency spring-boot-starter-oauth2-resource-server và issuer/JWK thực tế. Các đoạn trên là khung cấu hình cho bài mở rộng, chưa tích hợp vào Basic starter. Không chép URL placeholder rồi kỳ vọng ứng dụng chạy được. Prefix scope mặc định cần đối chiếu nếu hệ thống tùy biến converter.

Từ bearer header tới authority

  1. BearerTokenAuthenticationFilter lấy bearer token từ request và chuyển yêu cầu xác thực tới manager. Khác với Basic, đầu vào là token thay vì username/password.
  2. JwtAuthenticationProvider dùng JwtDecoder để đọc và xác minh chữ ký; các validator kiểm thời hạn, issuer và audience đã cấu hình. Decoder cần khóa công khai tin cậy từ test issuer. Resource server giữ phần xác minh, còn issuer giữ khóa ký.
  3. Khi token hợp lệ, converter ánh xạ scope thành authority. Ví dụ scope groups.read thành SCOPE_groups.read với converter mặc định. Authentication được đưa vào security context; rule của endpoint dùng authority này.

Ví dụ. Với API cấu hình audience directory-api, request GET /api/groups dùng token do test issuer phát, audience đúng, còn hạn và có groups.read trả 200 với danh sách nhóm đã seed. Cùng token hợp lệ về chữ ký/audience nhưng scope chỉ là profile thì qua được xác thực rồi bị rule endpoint từ chối với 403.

Access token, ID token và vòng đời

Client không mặc định đưa ID token tới API như access token. API cần token được phát cho đúng resource và policy. Token bearer bị lộ có thể bị dùng bởi người giữ token; không lưu token thật trong source, URL hoặc editor bài học. JWT ký không đồng nghĩa payload được mã hóa bí mật.

Token hết hạn, refresh, key rotation và thu hồi là các quyết định vận hành. Không hứa rằng xóa localStorage sẽ thu hồi mọi token còn hiệu lực. Nếu cần logout/thu hồi tức thời, đánh giá khả năng của provider, kiểu token và kiến trúc session thay vì chỉ thêm một nút trên frontend.

Bài thiết kế và ma trận kiểm thử

S3. Dùng một chain resource server với policy GET yêu cầu SCOPE_groups.read. Đọc seed danh sách nhóm của lab, cấu hình issuer và audience như ví dụ phía trên. Lập bảng dự đoán trước. Dùng token mẫu từ test issuer do bạn kiểm soát, tạo fixture có từng thuộc tính thay đổi độc lập và thực thi qua decoder thật. Với kiểm tra thời hạn, chọn token hết hạn vượt quá clock skew đã cấu hình.

Nộp riêng hai loại kết quả: ma trận HTTP qua decoder thật và test authorization với jwt() hoặc mock principal. Test mock giúp kiểm rule chọn đúng authority. Bằng chứng chữ ký, JWK, issuer và audience đến từ các ca thực thi decoder. Không ghi giá trị token vào kết quả.

Test thiếu scope dùng token hết hạn và nhận 401. Case nào thực sự đã được kiểm?

Decoder từ chối xác thực. Dùng token hợp lệ về thời hạn, issuer, audience và chữ ký rồi chỉ bỏ scope để chứng minh 403 từ authorization.

Phạm vi xác nhận: bài này cung cấp cơ chế và bài thiết kế; repo chưa chứa provider OAuth2/OIDC chạy kèm. Chỉ đánh dấu lab tích hợp đạt sau khi có môi trường và bằng chứng kiểm thử thực tế.

JWT có luôn tốt hơn session không?

Không. Chọn theo client, ranh giới hệ thống, nhu cầu thu hồi, độ phức tạp vận hành và nơi giữ credential. Một website đọc bài có thể dùng session phía server phù hợp mà không cần tự phát JWT.

Kiểm tra cách hiểu

Trước khi mở đáp án, hãy ghi dự đoán, lý do và dấu hiệu bạn sẽ dùng để kiểm chứng.

JWT đọc được nhưng sai đối tượng nhận

JWT hợp lệ về chữ ký và còn hạn, issuer đúng nhưng audience dành cho API khác. Resource server yêu cầu audience của mình. Kết quả nào đúng?

Mở đáp án và tiêu chí

Token không đạt xác thực cho resource server này vì sai aud. Test với token đúng aud và sai aud, cố định issuer và thời hạn.

Tự đánh giá. Chỉ ra vì sao decode và chữ ký hợp lệ chưa đủ để chấp nhận token.

Thiếu scope khác token hết hạn

API yêu cầu scope groups:write. So token hết hạn và token hợp lệ chỉ có groups:read trong cấu hình Bearer của bài.

Mở đáp án và tiêu chí

Token hết hạn không qua xác thực, thường 401 trong cấu hình đó. Token hợp lệ thiếu quyền bị từ chối ở authorization, thường 403. Test đi qua decoder thật cho ca hết hạn.

Tự đánh giá. Phân biệt lỗi token với policy quyền; chỉ ra ca nào test mock JWT không xác minh.

Ôn nhanh bằng trắc nghiệm
ID token có nên mặc định dùng thay access token để gọi API không?

Xem giải thích khi không dùng JavaScript

Không. ID token phục vụ client xác minh đăng nhập theo OIDC. API resource server cần access token đúng audience và policy.
