Mục tiêu và điều kiện học

Viết test phân biệt admin thiếu CSRF và reader đủ CSRF nhưng thiếu quyền.

Cần biết trước: Cookie, origin và authentication. Các bài ứng dụng có thể cần đọc trước phần dữ liệu tương ứng; dùng lộ trình để chọn kiến thức còn thiếu.

Baseline: Java 17 · Spring Boot 3.5.10 · Framework 6.2 · Security 6.5. Mỗi demo có hướng dẫn riêng; ví dụ H2 không chứng minh hành vi trên DB khác.

Admin có quyền nhưng POST vẫn trả 403

Admin đọc nhóm Backend để chuẩn bị thao tác ghi. GET thành công, POST với cùng danh tính lại trả 403. Dựa trên danh tính trong filter chain và ma trận quyền, bài này cô lập vai trò của session/token trước khi xét CORS.

HTTP stateless và phiên đăng nhập

HTTP không tự nhớ danh tính từ request trước. Ứng dụng có thể dùng cookie mang session ID; server dùng ID đó để khôi phục trạng thái phiên, trong đó có security context theo cấu hình. Cookie thường là định danh tham chiếu, không phải toàn bộ dữ liệu user. Session cần thời hạn, logout và chính sách cookie phù hợp.

Trong Spring Security 6, các cơ chế chuẩn xử lý việc lưu/khôi phục context. Nếu tự viết controller/filter đăng nhập rồi chỉ đặt Authentication vào SecurityContextHolder, không mặc định có đăng nhập bền cho request sau; phải làm đúng hợp đồng SecurityContextRepository và cơ chế liên quan. Vì vậy dùng cơ chế chuẩn trước khi tự viết auth.

HTTP Basic có thể kiểm credential ở mỗi request. Điều đó không chứng minh ứng dụng tuyệt đối không dùng session: ví dụ CSRF token có thể được lưu theo session. Hãy xem cấu hình và cookie thực tế thay vì gắn nhãn “stateless” chỉ vì dùng Basic.

CSRF xuất hiện khi trình duyệt tự gửi credential

Trình duyệt có thể đính cookie hoặc credential đã lưu vào request theo quy tắc của nó. Với thao tác ghi, ứng dụng dùng CSRF token để kiểm thêm giá trị gắn với ngữ cảnh ứng dụng. Hãy lập chính sách từ cách credential thực sự được gửi, rồi dùng ca thiếu token và token hợp lệ trong test cục bộ để chứng minh chính sách.

Spring Security mặc định bảo vệ các method không an toàn như POST. Trong lab, endpoint lấy token trả tên header và token; client giữ cùng cookie session khi gửi request ghi. Lấy token ở session A rồi gửi cookie session B có thể bị từ chối. Không log token và không copy token từ hướng dẫn như một hằng số.

Trên DB lab mới, tên chưa có thì trả group vừa tạo. Gọi lại cùng tên có thể bị unique constraint và trả 409 theo contract; đổi tên hoặc khởi động lại để làm lại. Bỏ token nhưng giữ admin và body hợp lệ: dự kiến 403, không tạo bản ghi.

Không quyết định tắt CSRF chỉ vì API “dùng JSON” hoặc “có JWT”. Phải xét credential được lưu và tự gửi thế nào, có cookie/Basic hay cơ chế khác, và bề mặt truy cập. Nếu API chỉ nhận bearer header do client đặt tường minh và không có credential tự gửi, mô hình rủi ro có thể khác; cấu hình cần phản ánh kiến trúc thực.

Cookie và token đi cùng nhau qua hai request

  1. GET /api/csrf: lab truy cập token, vì vậy repository có thể khởi tạo token cho session. Client giữ session cookie và nhận tên header cùng giá trị cần gửi.
  2. POST /api/groups: client giữ cùng session cookie và kèm header theo response GET. CsrfFilter áp yêu cầu bảo vệ lên POST, nạp token kỳ vọng và kiểm giá trị do client gửi qua token request handler.
  3. Nếu kiểm tra token đạt, chain có thể tiếp tục đến xử lý danh tính và quyền. Với thứ tự mặc định của solution, CSRF chạy trước Basic filter. Một 403 ở CSRF vì vậy chưa cho biết mật khẩu có hợp lệ.

Dự đoán bảng trước khi chạy solution cục bộ. Dùng một tên mới cho cả ba dòng và làm ca thành công cuối cùng. Với mỗi danh tính, tạo session từ GET token đúng credential của danh tính đó. Chụp status và đối chiếu số bản ghi; không đưa giá trị cookie hoặc token vào bằng chứng.

Giữ token nhưng lấy session mới, vì sao GET vẫn có thể 200 còn POST bị 403?

GET có thể được xác thực qua Basic và không đòi token CSRF ở lab. POST cần token đúng với phiên hiện tại. Kiểm lại header và cookie trước khi thay đổi role.

CORS giải quyết việc đọc response khác origin

Origin gồm scheme, host và port. http://localhost:3000 khác http://localhost:8181; localhost cũng khác 127.0.0.1. Trình duyệt có thể gửi preflight OPTIONS trước request cross-origin. Preflight không mang cookie xác thực như request nghiệp vụ thông thường nên CORS phải được xử lý đúng thứ tự trước security.

CORS không thay authentication, authorization hoặc CSRF, và không ngăn curl gọi API. Chọn allowlist origin/method/header theo nhu cầu. Khi dùng credentials, không cấu hình kiểu “cho tất cả” một cách tùy tiện; kiểm tra response header và request trong Network. Lab cùng origin chưa cần mở CORS cho frontend khác.

Ba thí nghiệm độc lập

  1. Admin + body hợp lệ, thiếu CSRF → 403. Xác nhận không có group mới.
  2. Reader + body và CSRF hợp lệ → 403 vì quyền ghi. Token hợp lệ không cấp role.
  3. Frontend origin khác gọi API: quan sát OPTIONS và console. Nếu curl chạy được nhưng trình duyệt không đọc response, xét CORS trước khi đổi password.
SameSite cookie có thay thế mọi bảo vệ CSRF không?

Không coi một thuộc tính cookie là lời giải cho mọi luồng. Nó là một lớp bảo vệ; cần xét trình duyệt, kiểu request, quan hệ site/origin và cách ứng dụng xác thực.

Bài tập lập trình

Viết test phân biệt admin thiếu CSRF và reader đủ CSRF nhưng thiếu quyền.

Cách sửa starter: Trong editor viết hai đoạn kiểm chứng liên tiếp và so dữ liệu sau mỗi request. Khi đưa vào bộ test thật, tách thành hai @Test với dữ liệu chuẩn bị riêng.

Tiêu chí kiểm chứng: Thử cùng session/token; kiểm dữ liệu không đổi sau hai request bị chặn.

Đoạn dưới là bài tập ngắn; các kiểu và phương thức liên quan cần nằm trong project của bài. Editor cho sửa, lưu nháp và tải file; không biên dịch hoặc chạy Java/Spring. Chạy test thật ở local theo hướng dẫn project.

Nháp tự lưu khi trình duyệt cho phép. Không nhập mật khẩu hoặc token thật.

Kiểm tra cách hiểu

Trước khi mở đáp án, hãy ghi dự đoán, lý do và dấu hiệu bạn sẽ dùng để kiểm chứng.

Hai ca cùng bị từ chối

Trong cấu hình lab yêu cầu ADMIN và CSRF cho POST. So admin thiếu token với reader có token hợp lệ. Làm sao biết nguyên nhân khác nhau?

Mở đáp án và tiêu chí

Admin thiếu token bị chặn ở CSRF. Reader có token hợp lệ vẫn thiếu quyền. Giữ body và endpoint giống nhau, đối chiếu với admin có token hợp lệ.

Tự đánh giá. Chọn biến đối chứng đúng và kiểm dữ liệu không đổi sau hai ca bị chặn.

Origin khác, cùng request

Request chạy được bằng HTTP client nhưng JavaScript khác origin không đọc response. Tách gì giữa CORS và quyền API?

Mở đáp án và tiêu chí

Xem Network để xác định preflight và header CORS. CORS là chính sách browser theo origin; quyền API được kiểm tra riêng bằng authentication/authorization. Test origin được phép và bị từ chối.

Tự đánh giá. Không suy từ client dòng lệnh thành hành vi browser; phân biệt hai lớp.

Ôn nhanh bằng trắc nghiệm
CORS có ngăn mọi client ngoài trình duyệt gọi API không?

Xem giải thích khi không dùng JavaScript

Không. CORS là cơ chế trình duyệt kiểm soát việc đọc response cross-origin; API vẫn cần authentication/authorization.
