Mục tiêu

Tự chứng minh API hoạt động qua từng request, trình bày cách thiết kế membership và trả lời được các câu hỏi về bean, DTO, phân trang và authentication.

Cần biết trước: Biết chạy demo và gọi API. Có thể đọc hợp đồng danh sách và luồng xử lý request.

Đề tự thi và tiêu chí đạt

Bạn triển khai danh bạ của một đội, có account và group. Từ cùng một lần chạy, hãy chứng minh account tạo được, có thể đổi nhóm, group có số đếm đúng, và request sai không làm mất dữ liệu đang có. Có thể dùng UI, Postman hoặc CLI; đầu ra kiểm tra là status, body, và một request đọc sau mỗi thay đổi quan trọng. Đây là đề tự luyện dựng từ các walkthrough, dùng thang tự chấm bên dưới.

  1. Đọc và tìm kiếm. Lấy group và số thành viên. Tìm linh trong danh sách account. Trình bày hợp đồng page/sort bằng API product và giải thích cách áp dụng cho account.
  2. CRUD. Tạo group Exam Team, đọc theo Location. Tạo account exam_user thuộc Backend và Exam Team. Sửa account để giữ Exam Team, bỏ Backend. Đọc số thành viên cả hai group, rồi xóa tài nguyên vừa tạo.
  3. Ca lỗi. Gửi tên trống, username trùng, group không có, và lặp lại request khi đăng nhập bằng reader. Sau mỗi lỗi quan trọng, dùng GET kiểm tra trạng thái dữ liệu.
  4. Giải thích. Chỉ vào controller, service, SQL hoặc repository và security chain. Dùng kết quả thực tế để giải thích tại sao đi tới đúng status.

Tự chấm 10 điểm: 2 điểm đọc/lọc/page, 3 điểm CRUD và đối chiếu membership, 3 điểm ca lỗi với kiểm tra dữ liệu, 2 điểm giải thích luồng. Tự đánh dấu đạt mục nào có thao tác tái lập được và giải thích được kết quả. Có thể thử trong 45 phút và để phần đáp án đóng cho đến khi kết thúc.

Đáp án thực hành có dữ liệu và kiểm chứng

Khởi động mới từ thư mục demo Buổi 17 bằng mvn -B -ntp package và java -jar target/springboot-lessons-demo-0.1.0.jar. Mặc định 127.0.0.1:8117, hai danh tính admin và reader dùng mật khẩu demo-pass. Seed H2 gồm Backend 2 thành viên, Ops 1, Empty 0. Account linh có hai group 1 và 2. Mỗi lần làm lại hoàn chỉnh, khởi động lại JAR để phục hồi seed. Tài khoản đăng nhập và account nghiệp vụ là hai tập riêng của demo.

Mở lời giải phần đọc và ghi

Chạy khối sau trong một terminal PowerShell 7. Giữ cùng phiên terminal để chạy tiếp các khối dưới. Hàm trả cả status và header để đối chiếu phản hồi.

$base = 'http://127.0.0.1:8117'
function BasicHeader($user) {
    'Basic ' + [Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes("${user}:demo-pass"))
}
$admin = @{ Authorization = (BasicHeader 'admin') }
$reader = @{ Authorization = (BasicHeader 'reader') }
$token = Invoke-RestMethod "$base/api/csrf" -Headers $admin -SessionVariable s
$admin[$token.headerName] = $token.token
$reader[$token.headerName] = $token.token
function Call-Exam($verb, $path, $data, $headers = $admin) {
    $options = @{ Uri = "$base$path"; Method = $verb; Headers = $headers; WebSession = $s; SkipHttpErrorCheck = $true }
    if ($null -ne $data) {
        $options.ContentType = 'application/json'
        $options.Body = ConvertTo-Json -InputObject $data -Depth 6 -Compress
    }
    Invoke-WebRequest @options
}
function Read-ExamJson($response) {
    [Text.Encoding]::UTF8.GetString($response.RawContentStream.ToArray()) | ConvertFrom-Json
}
Read-ExamJson (Call-Exam GET '/api/groups')
Read-ExamJson (Call-Exam GET '/api/accounts?q=linh')
Read-ExamJson (Call-Exam GET '/api/products/page?page=2&size=2')
$g = Call-Exam POST '/api/groups' @{ name='Exam Team' }
$groupPath = [string]($g.Headers.Location | Select-Object -First 1)
$gid = (Read-ExamJson $g).id
$g.StatusCode
(Read-ExamJson (Call-Exam GET $groupPath)).memberCount
$inputAccount = @{ username='exam_user'; email='exam@example.test'; groupIds=@(1,$gid) }
$a = Call-Exam POST '/api/accounts' $inputAccount
$accountPath = [string]($a.Headers.Location | Select-Object -First 1)
$a.StatusCode
(Read-ExamJson (Call-Exam GET $accountPath)).groupIds
$inputAccount.groupIds = @($gid)
$updated = Call-Exam PUT $accountPath $inputAccount
$updated.StatusCode
(Read-ExamJson (Call-Exam GET $accountPath)).groupIds
(Read-ExamJson (Call-Exam GET '/api/groups/1')).memberCount
(Read-ExamJson (Call-Exam GET $groupPath)).memberCount

Kỳ vọng kết quả đọc seed đúng như đề, product trang 2 trả [3,4] với 6 phần tử, 3 trang. 201 tạo group, đọc lại có 0 thành viên. 201 tạo account, đọc lại [1,gid]. 200 sửa account còn [gid], Backend trở về 2 thành viên, Exam Team là 1. Lấy ID qua phản hồi để bài chạy đúng cả khi DB cấp ID khác.

Mở lời giải ca lỗi và dọn dữ liệu 
$blank = Call-Exam POST '/api/groups' @{ name=' ' }
$dupe = Call-Exam POST '/api/accounts' @{ username='exam_user'; email='other@example.test'; groupIds=@() }
$missing = Call-Exam PUT $accountPath @{ username='changed_user'; email='other@example.test'; groupIds=@(99999) }
$forbidden = Call-Exam PUT $accountPath $inputAccount $reader
$blank,$dupe,$missing,$forbidden | Select-Object StatusCode
Read-ExamJson $blank | Select-Object code, errors
Read-ExamJson $dupe | Select-Object code
Read-ExamJson $missing | Select-Object code
Read-ExamJson (Call-Exam GET $accountPath)
(Call-Exam DELETE $groupPath).StatusCode
(Call-Exam PUT $groupPath @{ name='New Name' }).StatusCode
(Read-ExamJson (Call-Exam GET $accountPath)).groupIds.Count
(Call-Exam DELETE $accountPath).StatusCode
(Call-Exam GET $accountPath).StatusCode

Kỳ vọng 400 VALIDATION_FAILED, 409 CONFLICT, 404 NOT_FOUND, 403. Account vẫn là exam_user, email cũ và tập [gid]. Sau đó xóa group trả 204, sửa group vừa xóa trả 404, account còn 0 liên kết. Xóa account trả 204, đọc lại 404. PUT với group 99999 bị dừng khi kiểm tra group đích. Kết quả này kiểm chứng request thất bại không đổi dữ liệu; để kiểm chứng rollback sau một thao tác ghi, dùng ví dụ lỗi bước sau ở Buổi 7.

Giải thích các quyết định sau khi chạy

Tại Directory.java, Directory nhận DTO và gọi DirectoryService. Service kiểm các group đích, lưu account rồi so tập membership đang có với tập đích. Thuật toán có thể mô tả bằng Java dưới đây.

Set<Long> desired = new TreeSet<>(requestedIds);
Set<Long> toRemove = new HashSet<>(existingIds);
toRemove.removeAll(desired);
Set<Long> toAdd = new HashSet<>(desired);
toAdd.removeAll(existingIds);

Với cũ [1,2] và yêu cầu [2,3,3], tập đích là [2,3], xóa 1, thêm 3, giữ 2. Gửi lại cùng tập sau khi hoàn thành cho tập thêm/xóa rỗng. Khóa chính ghép (account_id, group_id) chặn liên kết trùng ở DB, hai FK bảo đảm hai phía tồn tại, transaction bao toàn bộ thay đổi. Sau khi xóa group, API dùng chính sách gỡ liên kết và giữ account. Muốn chặn xóa group còn người, thay đổi hợp đồng và kiểm thử cả đường xóa lại sau khi đã bỏ liên kết.

Nếu group trống biến mất khỏi danh sách hoặc đếm sai thành 1, xem truy vấn. LEFT JOIN giữ dòng group dù không có bản ghi khớp. COUNT(m.account_id) bỏ qua giá trị null trên dòng sinh thêm; COUNT(*) sẽ đếm dòng đó.

SELECT g.id, g.name, COUNT(m.account_id) AS member_count
FROM lab_groups g
LEFT JOIN lab_membership m ON m.group_id = g.id
GROUP BY g.id, g.name
ORDER BY g.id;

Gỡ ca cập nhật group lỗi: đọc URL, method, status và ID, sau đó gửi GET chính ID đó. Nếu GET trả 404, tạo group rồi dùng Location cho lần thử tiếp theo. Nếu GET 200 còn PUT 403, thử với admin đã lấy token và đối chiếu role. Nếu chỉ PUT 400, kiểm tra JSON và errors. Khi admin gửi tên trùng và nhận 409, dùng account mới với email khác để cô lập unique của username. DTO trả về chỉ công bố các trường client cần; mapping giảm dữ liệu trả về cho client, còn projection giảm cột đọc ở CSDL.

Tự kiểm tra

Tại sao demo đầu tiên nên có cả request sai?

Ca sai chứng minh đường xử lý lỗi, role và ràng buộc dữ liệu thực sự hoạt động. Một chuỗi status 200 chưa kiểm được các hợp đồng đó.

GET sản phẩm dùng page nhưng GET account chỉ tìm theo q. Khi trình bày nói thế nào?

Chỉ ra phạm vi hai endpoint. Để thêm page cho account, định nghĩa lại hợp đồng page/sort và count sau filter, rồi dùng các tập mẫu ở buổi ôn tập để kiểm thử.

Group vừa xóa trả 404 khi PUT, controller hay SQL quyết định?

Controller đưa ID xuống service. UPDATE 0 dòng vì ID không tồn tại làm service phát lỗi nghiệp vụ. Advice chuyển lỗi thành 404.

Tại sao nên dùng unique constraint dù đã kiểm trùng ở service?

Hai request có thể cùng đọc trạng thái chưa có rồi cùng insert. Unique tại DB ngăn ghi trùng ở thời điểm quyết định.

Trình bày Basic với DB trong ba bước?

Filter đọc credential, provider tra UserDetails theo username để có hash và role rồi so matches, filter chain dùng authorities để xét quyền route.

Entity và DTO khác gì trong bài này?

Entity đại diện dữ liệu persistence và có vòng đời theo persistence context. DTO định nghĩa dữ liệu qua biên API, có thể chứa tập ID, trường tổng hợp hoặc một phần dữ liệu.

Cấu hình ModelMapper qua @Bean cho phép làm gì?

Đăng ký đối tượng do factory method trả về để Spring quản lý và inject. Mapper vẫn cần kiểm tra mapping lồng và trường có tên khác bằng ví dụ cụ thể.

Sửa cùng groupIds hai lần có thể phát sinh liên kết trùng?

Phép hiệu tập không tạo thêm hàng ở lượt thứ hai. Khóa ghép tại DB là hàng rào cuối cùng cho dữ liệu. Các thao tác ghi đồng thời còn cần chính sách khóa hoặc xử lý xung đột nhất quán.
